# Expense Audit Skill — 原理科普与使用指南

> 版本：v0.1.1
> 适用对象：审计师、合规人员、财务 IT、HRSSC 共享服务中心、Agent Skill 集成方
> 阅读时长：约 20 分钟

---

## 第一部分：原理科普

### 1.1 这个 Skill 是用来做什么的

`expense-audit` 是一个**离线、确定性、可解释**的费用审计 Skill。它接收员工的报销明细（CSV 或 XLSX），做体检和标准化，然后跑 7 类规则，输出**带证据链的复核优先级清单**。

它**不**做这些事：
- 不直接批准、拒绝或追回任何报销
- 不联网查询工商、税务或发票真伪
- 不预设舞弊、虚假或违规结论
- 不替代人工对反证、合理解释和补充证据的判断

它的核心价值是把**几万行原始报销数据压缩成几十条结构化 finding**，让审计师能聚焦在 1% 的高风险记录上。

### 1.2 数据处理管线

```
┌─────────────────────────────────────────────┐
│  输入：expenses.csv / .xlsx + policy.json    │
└────────────────┬────────────────────────────┘
                 ▼

                 ▼

                 ▼
┌─────────────────────────────────────────────┐
│  第 4 步：跑 7 类规则（详见 1.3）             │

└────────────────┬────────────────────────────┘

```

### 1.3 七类规则详解

| # | 规则名 | 触发条件 | 默认优先级 | 证据强度 | 设计意图 |
|---|---|---|---|---|---|
| 1 | **exact-duplicate-invoice** | 同一发票号 + 同一币种 + 同一金额 | high (4) | strong | 最经典的"一票多报"或"虚开发票" |
| 2 | **exact-duplicate-employee-date-amount** | 同一员工 + 同一日期 + 同一币种 + 同一金额 | medium (3) | moderate | 单员工同日的重复报销 |
| 3 | **near-duplicate** | 同一员工 + 同一商户 + 窗口期内（默认 7 天） + 金额差异 ≤ 容差（默认 2%） | medium (2) | moderate | 调整金额规避阈值（"980 / 950 / 920"近似但都不超） |
| 4 | **policy-threshold** | 单笔费用 > 该 expense_type 适用制度上限 | medium (3) | strong | 制度超标（如酒店超 800 元/晚） |
| 5 | **split-expense** | 同一员工 + 同一商户 + 同一币种 + 窗口期（默认 3 天）内多笔合计 > 审批阈值（默认 900 元）**且任一单笔都 < 阈值** | medium (3) | moderate | 把一笔大额拆成多笔小额规避审批 |
| 6 | **weekend-signal** | 费用日期在周六/周日，且 `weekend_check=true` | low (1) | weak | 周末消费需要业务解释（值班、出差、客户现场） |
| 7 | **robust-outlier** | 同 peer group（expense_type + unit + region + currency）中位数偏离 robust z-score > 3.5 | medium (2) | moderate | 同类费用中的高额异常（MAD 稳健统计） |

### 1.4 为什么用 MAD 而不是普通 Z-score

很多场景里费用分布是**右偏**的（少量高价离群拉高均值），普通 Z-score 会被拉偏。**MAD（中位数绝对偏差）**对极端值不敏感：

```
robust_z = 0.6745 × (x - median) / MAD
```

- 普通 Z-score：均值偏移会污染比较
- MAD z-score：始终以中位数为锚，对离群稳健
- MAD = 0 时直接跳过该 group（避免除零）

这是审计统计学的常用选择，不是机器学习花招。

### 1.5 风险优先级与证据强度是两个独立维度

| 维度 | 含义 | 计算 |
|---|---|---|
| `risk_priority` | 复核优先级（high/medium/low/critical） | 从 finding 的 risk_score（1-6+）映射 |
| `evidence_strength` | 证据本身的可信度（strong/moderate/weak） | 由规则类型决定（如银行账号共享=strong，地址共享=weak） |

**这两个维度故意分开**：高金额未必有强证据，强证据未必金额高。一个 5 万元的发现可能是 solid evidence（系统记录、时间戳），但一个 50 万元的发现也可能是 weak evidence（仅口头说法、文件模糊）。

审计师阅读时应**先看 high+strong 的组合**——这是"必须立刻复核"的最强信号。

### 1.6 Evidence 双向引用机制

每条 finding 至少引用一条 evidence；每条 evidence 都能精确回溯：

```json
{
  "evidence_id": "EV-000003",
  "source_file": "expenses.csv",
  "source_hash": "sha256:d47c4079ec14b...",
  "row": 2,
  "field": "amount",
  "value": 920.0,
  "extraction_method": "normalized",
  "confidence": 1.0
}
```

审计师从 finding 跳到 evidence，再从 evidence 跳回源数据**任何一行**，是这套 skill 的**核心可追溯性保障**。

### 1.7 不确定性原则：脚本不形成最终判断

所有 finding 都是"**复核线索**"而不是"舞弊认定"。脚本做的事：
- 找异常 → 标记 priority + evidence_strength
- 列替代解释 → 制度缺失/冲销/退款/紧急采购等

脚本不做的事：
- 不写"已证实舞弊""虚假报销""拒付"
- 不计算"舞弊金额""损失金额"
- 不发起审批、扣款、停职等动作

这是设计原则：AI 给线索，人做判断。

## 第二部分：使用指南

### 2.1 前置准备

#### 环境要求

- Python ≥ 3.10
- 标准库（csv/hashlib/json/statistics/datetime 等）无需安装
- 仅当输入是 XLSX 时需要：`pip install openpyxl`
- **完全离线**——不会发起任何网络请求

#### 检查环境

```bash
python3 scripts/run_expense_audit.py --check-env
```

会返回：

```json
{
  "python": "3.11.0",
  "recommended": ">=3.10",
  "xlsx_support": "available (3.0.10)",
  "network_required": false
}
```

### 2.2 输入准备

#### 2.2.1 报销数据 CSV / XLSX

至少包含以下 4 个**核心字段**：

| 字段 | 含义 | 必填 |
|---|---|---|
| `expense_id` | 单据唯一编号 | ✅ |
| `employee_id` | 员工编号 | ✅ |
| `amount` | 报销金额 | ✅ |
| `expense_date` | 费用发生日期 | ✅ |

强烈推荐补充以下字段（影响 finding 质量）：

| 字段 | 含义 |
|---|---|
| `expense_type` | 费用类型（hotel/meal/office/travel/taxi 等） |
| `currency` | 币种 |
| `vendor_name` | 商户名称 |
| `invoice_number` | 发票号 |
| `approver` | 审批人 |

中英文字段别名自动支持，例如：

```csv
报销单号,工号,金额,发生日期,...
BCN-001,Z001,920,2026-06-01,...
```

会自动映射为 `expense_id`、`employee_id`、`amount`、`expense_date`。

#### 2.2.2 制度配置 policy.json

```json
{
  "policy_version": "YOUR-COMPANY-POLICY-1.0",
  "default_currency": "CNY",
  "limits": [
    {"rule_id": "HOTEL-PER-CLAIM", "expense_type": "hotel", "currency": "CNY", "max_amount": 800}
  ],
  "approval_thresholds": [
    {"rule_id": "GENERAL-APPROVAL", "currency": "CNY", "amount": 900}
  ],
  "near_duplicate_window_days": 7,
  "near_duplicate_amount_tolerance": 0.02,
  "split_window_days": 3,
  "weekend_check": true,
  "outlier_min_group_size": 5,
  "outlier_robust_z": 3.5
}
```

| 字段 | 说明 |
|---|---|
| `limits[]` | 单笔费用上限，按 (expense_type, currency) 匹配 |
| `approval_thresholds[]` | 触发 split-expense 的阈值 |
| `near_duplicate_window_days` | near-duplicate 时间窗口 |
| `near_duplicate_amount_tolerance` | near-duplicate 金额容差（0.02 = 2%） |
| `split_window_days` | split-expense 时间窗口 |
| `weekend_check` | 是否启用 weekend-signal |
| `outlier_min_group_size` | peer group 最少样本数（小样本不报离群） |
| `outlier_robust_z` | robust z-score 阈值（默认 3.5） |

**如果没有 policy**：脚本会用默认参数，但 `policy-threshold` 和 `split-expense` 会被跳过（manifest 的 `skipped_rules` 会写明）。

### 2.3 执行命令

```bash
python3 scripts/run_expense_audit.py \
  --input /path/to/expenses.csv \
  --policy /path/to/policy.json \
  --output /path/to/new-output-directory
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `--input` | ✅ | CSV / XLSX 文件路径 |
| `--policy` | 推荐 | policy.json 路径 |
| `--output` | ✅ | 输出目录（必须为空或不存在） |
| `--field-map` | 可选 | 手动指定字段映射 JSON |
| `--sheet` | 可选 | XLSX 工作表名 |

### 2.4 输出解读顺序

按以下顺序阅读 8 个产物：

```
1. summary.md           → 一段话看完概要（finding 总数 + 优先级分布 + 类型分布）
2. data_quality.md      → 数据健康度（坏行、字段映射、空值率）
3. run_manifest.json    → 运行参数 + 输入 SHA-256 + 跳过的规则
4. findings.csv         → 所有 finding（按 finding_id 排序）
5. findings.jsonl       → 同 findings.csv 的 JSON 行格式
6. evidence.jsonl       → 每条 finding 引用的 evidence 详细记录
7. clean_expenses.csv   → 标准化后的可用数据
8. bad_rows.csv         → 解析失败的记录（不可忽略——可能是系统性问题）
```

### 2.5 推荐的复核流程

**第 1 步：看 summary.md**

先看 finding 总量。如果数量异常多（如几千条），说明：
- 阈值可能太严
- 数据质量问题（重复导入）
- 制度需要重新校准

如果数量很少（< 10 条），也可能：
- 制度宽松，金额阈值过高
- 数据本身干净

**第 2 步：聚焦 high + strong**

打开 findings.csv，筛选 `risk_priority=high AND evidence_strength=strong`。这些是**必须立刻复核**的。

**第 3 步：按主体合并**

同一个员工、同一商户的多个 finding 应该合并阅读。例如：
- 同一员工同一商户：3 个 near-duplicate + 1 个 policy-threshold
- 暗示模式：金额持续接近上限，可能故意调整

**第 4 步：检查反证和替代解释**

每个 finding 的 manifest 中包含 `open_questions` 字段（需要补齐的证据）和 `alternative_explanations` 字段（可能的合理解释）。在形成判断前先穷尽这些。

**第 5 步：补充证据**

常见的补证清单：
- 发票影像（看是否真实开票）
- 报销状态（是否已退款/冲销）
- 业务审批记录（是否经部门负责人批准）
- 行程证明（酒店对应差旅申请、出租车对应行程单）

### 2.7 已知边界与限制

| 边界 | 说明 | 应对 |
|---|---|---|
| **仅基于原始数据** | 不联网查工商、不查发票真伪 | 补证环节人工查验 |
| **金额文本字段需可解析** | `abc`、`¥1,200.00`、`$50` 等格式支持，但 `"待定"` 这种无法解析 | 标准化失败进 bad_rows.csv，不静默删除 |
| **币种混算不归一** | USD 和 CNY 单独识别，不按汇率换算 | 制度按币种精确匹配（policy-threshold 必须 currency 一致） |
| **负数（退款）保留原值** | -950 元不会被自动解释为"冲销原 950 元" | 审计师人工关联同一发票号的正负记录 |
| **MAD = 0 时跳过离群** | 整个 peer group 金额完全相同（罕见但可能） | 在 manifest 记录跳过原因 |
| **小样本不报离群** | peer group 样本数 < min_group_size 时跳过 | 默认 5，可调小但会引入噪声 |
| **near-duplicate 只比同员工** | 跨员工同商户同金额不被识别 | 由 exact-duplicate-invoice 覆盖 |
| **不识别"金额故意微小调整"** | 仅按 % 容差，不做统计异常模式 | 这是 near-duplicate 的扩展方向 |

### 2.8 故障排查

| 错误 | 原因 | 解决 |
|---|---|---|
| `无法解析 CSV` | 编码错误 | 确保 CSV 是 UTF-8 编码（脚本兼容 BOM） |
| `读取 XLSX 需要 openpyxl` | 缺依赖 | `pip install openpyxl`（仅 XLSX 输入需要） |
| `输出目录非空` | 输出目录已有文件 | 换新目录；脚本不覆盖历史运行 |
| 0 个 finding | 制度阈值过宽 或 数据本身就干净 | 调整 policy 后重跑；先查 data_quality.md |
| finding 数量爆炸（> 1000） | 数据质量差 / 阈值过严 | 检查 data_quality.md 的空值率；放宽容差 |
| `bad_rows > 0` | 关键字段解析失败 | 打开 bad_rows.csv 看 `reasons` 列；可能是源系统导出格式变化 |

## 第三部分：审计视角的最佳实践

### 3.1 不应该把脚本当"判决书"

脚本找到 100 条 finding 是正常现象。审计师的工作不是"修复 100 条"，而是：
1. **优先级排序**：先处理 high+strong
2. **模式识别**：合并同一主体、同一模式
3. **真相还原**：每个 finding 都可能是冰山一角或一场误会
4. **制度反馈**：多次出现"误报"的规则需要调整 policy

### 3.2 跟现有审计流程的关系

```
月初跑脚本
   ↓
审计师看 summary.md 选 high+strong
   ↓
抽样核查（10-30%）
   ↓
补充核查清单 → 现场访谈/调阅凭证
   ↓
形成月度审计结论
   ↓
更新 policy.json（如发现阈值不当）
```

### 3.3 数据治理建议

如果你的数据是 ERP 导出的：
- 确保 `expense_id` 真正唯一
- 同一字段不要混用中英文（如 expense_id 用"BCN-001"，有些行却用纯数字"12345"）
- 日期格式统一（建议 ISO 8601）
- 金额字段不要混入货币单位（"¥920" 应在 currency 字段，amount 应是纯数字）

### 3.4 跟其他 Skill 配合

- **发现某员工的费用异常**（expense-audit）→ **追溯该员工的供应商关联**（procurement-fraud）→ **触发调查工作空间**（investigation-assistant）
- 这三个 skill 的 handoff 是单向的：上游 skill 标记"建议调查"，下游 skill 需要人工授权才启动
