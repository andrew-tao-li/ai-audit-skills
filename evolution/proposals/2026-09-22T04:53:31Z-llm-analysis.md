# 审计 Skill 失败案例分析报告

> 分析对象：11 个失败案例（8 个 false_positive + 3 个 false_negative）
> 涉及 Skill：`expense-audit`、`procurement-fraud`
> 说明：以下根因基于 `finding_type` 语义 + fixture 场景命名 + 常见审计规则实现模式进行**推测**，具体行号需对照 `run_expense_audit.py` / `run_procurement_audit.py` 实际代码确认。

---

## 一、Expense Skill 失败（7 例）

### 失败 #1 — `complex_01_full_audit` / split-expense / false_positive

**1. 根因推测**
`split-expense` 规则通常按「同一供应商 + 时间窗口 + 金额阈值」聚合。在 `full_audit` 这种多场景混合 fixture 中，很可能：
- 时间窗口过宽（如 7 天/30 天），把**正常的多笔独立报销**误判为拆分；
- 或聚合键缺少 `category` / `employee_id`，把不同员工、不同类目的报销合并计数；
- 或阈值判定用了 `>=` 而非 `>`，边界值触发误报。

**2. 修复方向**
- 在 `run_expense_audit.py` 的 `detect_split_expense()` 中收紧聚合键：`(vendor, employee_id, category)`；
- 时间窗口从宽窗口改为**同一天或相邻 2 天**；
- 增加「拆分意图」二次校验：仅当**每笔金额都低于审批阈值**且**合计超过阈值**时才报；
- 对 `full_audit` fixture 增加白名单/豁免逻辑（如差旅分次报销）。

**3. 风险评估**
- 收紧窗口可能漏掉真正的「跨周拆分」→ 引入 false_negative；
- 增加二次校验会降低召回率，需在 `complex_02` 上回归验证；
- 白名单若硬编码 fixture 名称，会污染生产逻辑，应改为**规则参数化**。

### 失败 #2 — `complex_02_procurement_abuse` / robust-outlier / false_positive

**1. 根因推测**
`robust-outlier` 一般用 MAD / IQR 检测异常金额。在 `procurement_abuse` 场景中，**真实欺诈本身就会拉高分布**，导致：
- 用**全体样本**计算中位数/MAD，把正常大额采购（如设备）判为离群；
- 未按 `category` 分组，跨类目比较金额（差旅 vs 设备）；
- MAD 缩放因子 `1.4826` 或阈值 `3.5` 设置过松。

**2. 修复方向**
- 在 `detect_robust_outlier()` 中**按 category/vendor 分组**计算统计量；
- 使用**稳健阈值**（如 MAD > 3.5 且绝对金额超过类目 P95）；
- 排除已知大额类目（capex）或引入 `min_amount` 下限；
- 对 `procurement_abuse` fixture 检查是否因**注入的欺诈样本**污染了基线。

**3. 风险评估**
- 分组后小样本组统计不稳定 → 需设 `min_group_size`；
- 提高阈值会漏掉真实异常 → 与 #9 `price-outlier` false_negative 联动，需统一调参。

---

### 失败 #3 — `complex_02_procurement_abuse` / sequential-invoice / false_positive

**1. 根因推测**
`sequential-invoice` 检测连号发票。误报常见原因：
- 只比对**发票号数值差 = 1**，未排除**同一批次正常连号**（如批量采购同一供应商）；
- 未结合时间/金额，把「同一天多张连号」误判；
- 未排除**作废/重开**发票。

**2. 修复方向**
- 在 `detect_sequential_invoice()` 中增加复合条件：连号 **且** 金额相近 **且** 时间集中 **且** 供应商相同；
- 引入「连号密度」指标（如 3 张以上连号才报）；
- 排除 `status in ('void', 'reissued')` 的记录。

**3. 风险评估**
- 复合条件过严 → 漏掉「连号但金额不同」的欺诈；
- 需要与 `near-duplicate`（#4）区分，避免规则重叠导致重复报或互相抵消。

---

### 失败 #4 — `complex_02_procurement_abuse` / near-duplicate / false_negative ⚠️

**1. 根因推测**
漏报 `near-duplicate` 通常因为：
- 相似度算法**阈值过高**（如要求 > 0.95），而实际欺诈是「金额微调 + 日期偏移」；
- 只做**精确字段比对**（invoice_no 完全相等），未做模糊匹配；
- 未对**金额做归一化**（如 1000 vs 1000.00 vs 1,000）；
- 未考虑**供应商名称变体**（"ABC Ltd" vs "ABC Limited"）。

**2. 修复方向**
- 在 `detect_near_duplicate()` 中引入**多字段加权相似度**：`vendor(0.4) + amount(0.3) + date(0.2) + desc(0.1)`；
- 阈值下调至 **0.85** 并做 A/B 验证；
- 金额先归一化（去千分位、统一小数）；
- 供应商名做标准化（去后缀、大小写、缩写）。

**3. 风险评估**
- 阈值下调会显著增加 false_positive（与 #1/#2/#3 同 fixture 冲突）；
- 需与 `exact-duplicate-invoice`（#5）做**优先级去重**，避免同一对记录被两条规则同时命中；
- 模糊匹配性能开销上升，需评估大数据量下的耗时。

### 失败 #5 — `complex_03_hr_falsified` / exact-duplicate-invoice / false_positive

**1. 根因推测**
`exact-duplicate-invoice` 误报在 HR 场景中常见于：
- **同一发票号被合法复用**（如分期付款、部分报销）；
- 未区分**发票号 vs 报销单号**，字段映射错误；
- 未排除**同一 employee 的多次提交**（草稿→正式）；
- 大小写/空格未 trim 导致「伪重复」。

**2. 修复方向**
- 在 `detect_exact_duplicate()` 中增加**去重键**：`(invoice_no, employee_id, submit_date)`；
- 排除 `status == 'draft'` 或 `superseded_by` 不为空的记录；
- 对 invoice_no 做 `strip().upper()` 标准化；
- 增加「同一发票多次报销」的**业务豁免**（如分期）。

**3. 风险评估**
- 加入 employee_id 后可能漏掉**跨员工盗用发票**的真实欺诈；
- 需保留一条「跨员工同发票」的高优先级告警作为补偿。

---

### 失败 #6 — `complex_03_hr_falsified` / policy-threshold / false_positive

**1. 根因推测**
`policy-threshold` 误报通常因为：
- 阈值比较用了**含税金额**而政策是**不含税**；
- 未按**职级/地区**区分阈值（HR 场景常见）；
- 边界值处理错误（`>=` vs `>`）；
- 未考虑**多币种**，直接比较数值。

**2. 修复方向**
- 在 `check_policy_threshold()` 中明确：`amount_basis = 'pre_tax'`；
- 阈值表按 `(grade, region, category)` 索引；
- 统一用 `Decimal` 比较，避免浮点误差；
- 多币种先换算为基准币再比较。

**3. 风险评估**
- 引入职级/地区维度后，**阈值表维护成本上升**；
- 若 fixture 未提供职级字段，需 fallback 到默认阈值，可能仍误报。

---

### 失败 #7 — `complex_03_hr_falsified` / submit-before-expense / false_positive

**1. 根因推测**
`submit-before-expense` 检测「提交时间早于消费时间」。误报原因：
- **时区未统一**（提交用 UTC，消费用本地时间）；
- 日期解析格式不一致（`YYYY-MM-DD` vs `DD/MM/YYYY`）；
- 未考虑**预审批/预支**场景（合法提前提交）；
- 消费日期为空时被当作 0 处理。

**2. 修复方向**
- 在 `detect_submit_before_expense()` 中统一时区为 UTC 或业务本地时区；
- 用 `dateutil.parser` 做鲁棒解析，解析失败则跳过并记录；
- 增加 `is_prepaid` / `pre_approval_id` 字段豁免；
- 对空日期显式跳过，不参与比较。

**3. 风险评估**
- 时区统一可能改变历史数据判定结果，需回归全量 fixture；
- 豁免逻辑若过宽，会漏掉真实「倒填日期」欺诈。

## 二、Procurement Skill 失败（4 例）

### 失败 #8 — `complex_01_ma_carton` / split-order / false_positive

**1. 根因推测**
`split-order` 与 expense 的 `split-expense` 类似，但采购场景中：
- **M&A 场景**下多主体分别下单是**合法**的（不同法人实体）；
- 聚合键缺少 `legal_entity` / `cost_center`；
- 时间窗口把**季度采购**误判为拆分；
- 未排除**框架协议下的分批下单**。

**2. 修复方向**
- 在 `detect_split_order()` 中聚合键加入 `legal_entity`、`cost_center`、`contract_id`；
- 若存在**框架合同**，则豁免拆分判定；
- 时间窗口收紧至 **72 小时**；
- 增加「合计金额是否超过审批权限」的二次校验。

**3. 风险评估**
- 加入 legal_entity 后可能漏掉**跨主体规避审批**的真实欺诈；
- 框架合同豁免若被滥用，会成为新的规避通道。

---

### 失败 #9 — `complex_01_ma_carton` / price-outlier / false_negative ⚠️

**1. 根因推测**
漏报 `price-outlier` 常见原因：
- 用**全局均价**做基线，M&A 场景下多主体价格差异大，异常被稀释；
- 未按 `(item, unit, currency)` 分组；
- 未考虑**数量折扣**（大单单价低是正常的）；
- 阈值过松（如 > 3σ），而欺诈只偏离 1.5σ。

**2. 修复方向**
- 在 `detect_price_outlier()` 中按 `(item_code, uom, currency, region)` 分组；
- 引入**数量-价格回归**，用残差判定异常而非绝对价格；
- 阈值改为 **P95/P5 分位 + 绝对偏离**双条件；
- 对 M&A fixture 检查是否因**多主体混合**导致基线失真。

**3. 风险评估**
- 分组过细导致样本不足 → 需 `min_samples` 回退到上级分组；
- 回归模型引入复杂度，需评估可解释性（审计场景要求可追溯）。

---

### 失败 #10 — `complex_02_emergence` / process-order-before-approval / false_positive

**1. 根因推测**
`process-order-before-approval` 检测「先下单后审批」。紧急采购（emergence）场景下：
- **紧急采购允许事后补审批**，规则未识别 `is_emergency` 标志；
- 时间比较用了**审批完成时间**而非**审批发起时间**；
- 未考虑**口头/邮件审批**的补录；
- 时区/格式问题（同 #7）。

**2. 修复方向**
- 在 `detect_process_before_approval()` 中增加 `is_emergency` / `emergency_reason` 豁免；
- 审批时间取 `min(approval_initiated_at, approval_completed_at)`；
- 引入**宽限期**（如紧急采购 48 小时内补审批视为合规）；
- 统一时间解析逻辑（复用 #7 的修复）。

**3. 风险评估**
- 紧急豁免可能被滥用为「先斩后奏」通道 → 需限制豁免次数/金额；
- 宽限期设置需与合规部门确认，否则审计口径不一致。

---

### 失败 #11 — `complex_02_emergence` / process-receipt-before-approval / false_negative ⚠️

**1. 根因推测**
漏报 `process-receipt-before-approval`（先收货后审批）：
- 规则只检查了 **order** 与 approval 的时序，**未覆盖 receipt**；
- 或 receipt 表与 approval 表**未 join**，字段缺失导致跳过；
- 紧急采购豁免逻辑（#10 的修复）**过度泛化**，把 receipt 也一并豁免；
- 收货时间字段为空时被静默跳过。

**2. 修复方向**
- 在 `detect_process_before_approval()` 中**显式覆盖三类事件**：`order`、`receipt`、`payment`；
- 确保 receipt 与 approval 通过 `po_id` 正确 join；
- 紧急豁免**仅适用于 order**，receipt 仍需审批（或单独规则）；
- 对空时间字段记录 warning 而非静默跳过。

**3. 风险评估**
- 与 #10 的修复**直接冲突**：豁免范围界定不清会导致「修好一个坏一个」；
- 建议将豁免逻辑**参数化**（`exempt_event_types=['order']`），并加单元测试锁定行为；
- 需回归 `complex_02` 全量用例，确认 #10 与 #11 同时通过。

## 三、横向观察与系统性建议

| 模式 | 涉及失败 | 建议 |
|---|---|---|
| **聚合键缺失**（未按 category/entity/employee 分组） | #1, #2, #8, #9 | 统一引入 `group_by` 参数化配置 |
| **时间处理不一致**（时区/格式/字段选择） | #7, #10, #11 | 抽出 `parse_time()` 公共工具，全 Skill 复用 |
| **豁免逻辑过度泛化** | #10 ↔ #11 | 豁免必须**按事件类型白名单**，禁止全局 flag |
| **阈值/相似度调参冲突** | #4 ↔ #1/#2/#3 | 建立**回归测试矩阵**，任何调参必须全 fixture 通过 |
| **规则重叠未去重** | #3 ↔ #4, #5 ↔ #4 | 引入 finding 优先级与去重层 |

**优先级建议**：
1. **P0**：#11（false_negative，且与 #10 修复冲突，需一并处理）
2. **P0**：#4、#9（false_negative，漏报欺诈风险最高）
3. **P1**：#1、#2、#8（false_positive 集中，规则聚合键问题）
4. **P2**：#5、#6、#7、#10（单点误报，可独立修复）

**通用风险**：所有修复都需在**全量 fixture 回归**后合入，避免「按下葫芦浮起瓢」——本批 11 个失败中已出现至少 3 组互斥修复（#4↔#1/2/3、#10↔#11、#5↔#4），必须用测试矩阵锁定。
