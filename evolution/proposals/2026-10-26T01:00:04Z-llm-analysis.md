> 仅依据 `finding_type`、`fixture` 和当前 Skill 结构推测；未提供源码，以下“代码段”指建议检查/修改的位置，不等同于已确认的具体行号。  
> 共同现象是全部为 `false_negative`：预期发现异常，但审计流程未产出对应 finding。最可能存在三类共性根因：  
> 1. 异常规则未接入执行入口、规则名映射不一致，或异常结果被过滤；  
> 2. 字段标准化/关联键/日期逻辑错误；  
> 3. 单规则 fixture 可检出，但组合 fixture 因短路、上下文缺失或只保留首要异常而漏报。

# 一、逐项分析

## 01. `expense / 01_duplicate_invoice / exact-duplicate-invoice`

- **根因推测**
  - 重复检测可能仅依赖数据库唯一约束，或只比较原始发票号，未做规范化。
  - 也可能检测到了重复记录，但没有转换成 `finding_type=exact-duplicate-invoice`，导致结果落盘时被当作普通信息丢弃。
  - 缺少发票号、金额、日期字段时，重复键生成返回空值，规则被跳过。

- **修复方向**
  - 在 `scripts/run_expense_audit.py` 的重复检测段建立规范化指纹，例如：
    - 发票号：去空格、统一大小写、去除不可见字符；
    - 金额：统一币种并转换定点小数；
    - 日期：统一为 ISO 日期；
    - 商户/税号：标准化后参与比较。
  - 优先按“供应商税号 + 规范化发票号”判重，再辅以“供应商 + 日期 + 金额 + 税号”。
  - 检查异常到输出的映射层，确保 `exact-duplicate-invoice` 写入最终 findings，而不是只写内部 warning。
  - 对重复组保留 `invoice_ids/group_id`，避免同一重复组只输出一条造成 fixture 计数不匹配。

- **风险评估**
  - **中高风险**：过度归一化可能把合法同号票据误判为重复。
  - 字段缺失时若使用空字符串参与比较，会造成大规模假阳性。
  - 指纹过宽会把不同供应商或不同日期的独立消费合并。

## 02. `expense / 02_employee_date_amount / exact-duplicate-employee-date-amount`

- **根因推测**
  - 规则可能只实现“发票号重复”，没有实现“员工 + 日期 + 金额”的业务重复。
  - 员工标识可能同时存在 `employee_id`、`user_id`、姓名，导致关联失败。
  - 金额比较使用浮点数或字符串，未统一币种、税费和小数格式。

- **修复方向**
  - 在重复检测模块新增独立规则：
    - 规范员工主键；
    - 规范交易日期；
    - 金额转为整数分或 `Decimal`；
    - 按 `(employee_key, expense_date, amount)` 分组，组内至少两条即产生 finding。
  - 复用明确的员工维度映射，不要在规则内直接使用姓名。
  - 若同组内发票号不同，finding 仍应标为 `exact-duplicate-employee-date-amount`，不要被发票号判重规则覆盖。
  - 将各规则结果合并后统一输出，不允许“重复检测已找到”但未映射到该 finding type。

- **风险评估**
  - **中风险**：同日同金额但确属不同费用的真实消费可能被误报。
  - 若忽略费用类型或商户，误报率会进一步升高。
  - 建议加入同商户、同费用类型等约束，或将结果标为需复核异常。

## 03. `expense / 03_sequential_invoices / sequential-invoice`

- **根因推测**
  - 连续编号检测未实现，或只检测单据编号本身。
  - 编号解析未处理前缀、日期段、混合字母数字、补零和编号长度变化。
  - “连续”可能错误要求完全相邻，而 fixture 暗示存在票号序列模式。

- **修复方向**
  - 在 `run_expense_audit.py` 新增票号解析器：
    - 提取固定前缀和数字后缀；
    - 识别数字段递增；
    - 支持同一员工、供应商或短时间窗口内的小间隔序列；
    - 对补零编号先去掉前导零再转整数。
  - 将序列成员关联为一个 group，并输出缺失号、增量或异常间距。
  - 与 `exact-duplicate-invoice` 分开：重复规则和序列规则应并行执行。

- **风险评估**
  - **中风险**：正常批量开票、供应商分批出票可能形成合法序列。
  - 仅按数字后缀递增可能把不同年份、不同前缀票据串联。
  - 窗口过大、供应商范围过宽会显著增加假阳性。

## 04. `expense / 04_format_anomaly / invoice-format-anomaly`

- **根因推测**
  - 缺少发票格式校验规则。
  - 校验逻辑可能只验证金额或日期，没有校验发票号模式。
  - 格式异常可能仅作为数据质量提示，未提升为正式 finding。

- **修复方向**
  - 在数据标准化后、异常规则执行前增加 schema/格式验证层。
  - 按供应商或国家/地区配置发票号正则，检查：
    - 长度；
    - 字符集；
    - 固定前缀；
    - 数字段数量与补零规则。
  - 对不匹配记录产生 `invoice-format-anomaly`，包含字段、期望格式和实际值。
  - 规则应支持配置化白名单，避免硬编码单一发票格式。

- **风险评估**
  - **中高风险**：各国税制、供应商系统和历史格式不同，硬编码正则易误报。
  - 缺失字段与真正格式错误应区分处理。
  - 建议按供应商/地区逐步启用，并对新格式告警而不直接阻断。

## 05. `expense / 05_holiday / holiday-signal`

- **根因推测**
  - 节假日判断可能只支持周末，不支持法定节假日。
  - 节假日数据未加载、时区不一致，或使用了错误的 holiday calendar。
  - `holiday-signal` 没有接入最终 finding 映射。

- **修复方向**
  - 在日期分类模块中实现 `weekday / weekend / holiday / working-day` 四态。
  - 节假日应来自可配置日历，并指定国家/地区及年份。
  - 统一业务时区后再判断本地日期。
  - 当消费发生在节假日时生成 `holiday-signal`；注意现有 fixture 多为 `weekend-signal`，需分别测试两套规则。

- **风险评估**
  - **中风险**：调休工作日、地区差异和临时假日会造成误判。
  - 日历版本错误或年份缺失会导致漏报。
  - 周末与节假日重叠时可能重复产生多个 finding，影响计数。

## 06. `expense / 06_submit_before_expense / submit-before-expense`

- **根因推测**
  - 审计没有比较 `expense_date` 与 `submitted_at`。
  - 日期字段可能是字符串，未转换为可比较的 `date/datetime`。
  - 字段名存在多个候选，但代码只读取了其中一个。
  - 组合 fixture 中可能因流程状态过滤导致记录未进入比较。

- **修复方向**
  - 在 `run_expense_audit.py` 的时间一致性校验中显式比较：
    - `submitted_at < expense_date`：提交早于消费；
    - 如存在 `occurred_at`，使用业务发生时间作为主字段。
  - 统一时区并明确仅有日期时的比较语义。
  - 对空值、解析失败单独记录数据质量问题，不要默认为合法。
  - 在进入审批、金额等规则前先执行该检查，避免规则短路掩盖异常。

- **风险评估**
  - **中风险**：跨时区、补录、预授权场景可能形成假阳性。
  - 若只有日期没有具体时间，“当天提交”不应判为早于。
  - 字段解析错误可能扩大误报或造成异常抛出。

## 07. `expense / 07_future_date / future-date`

- **根因推测**
  - 未建立审计基准日期，未来日期仅与系统当前时间比较，且测试环境时间不稳定。
  - 未来日期判断被限制为“超过固定天数”，fixture 的偏移量未达到阈值。
  - 记录可能因状态或未来日期被过滤，导致规则拿不到数据。

- **修复方向**
  - 引入可注入的 `audit_as_of_date`，测试与生产分别传入基准时间。
  - 规则定义为 `expense_date > audit_as_of_date`，不要依赖隐式 `datetime.now()`。
  - 如业务允许预提，可配置宽限天数，但应另行标记而非静默忽略。
  - 确保未来日期记录仍进入所有适用规则，不要在数据清洗阶段剔除。

- **风险评估**
  - **低到中风险**：基准时间选择不当会造成系统性误报。
  - 预授权、预订未来服务可能合法。
  - 时区转换可能使边界日期偏移一天。

## 08. `expense / 08_self_approval / self-approval`

- **根因推测**
  - 审批人字段与申请人/员工字段没有使用同一主键规范。
  - 规则可能只比较姓名；同名人员会造成错误或漏判。
  - 代理审批、多人审批链或审批角色未被建模。
  - 审批记录可能存于单独表，脚本只扫描费用表或只扫描当前状态。

- **修复方向**
  - 在 `run_expense_audit.py` 中统一解析 applicant、employee、approver 为主键。
  - 对单笔费用检查所有审批人；任一审批人与申请人相同即产生 `self-approval`。
  - 明确代理审批例外：只有经授权代理关系覆盖时才能豁免。
  - 若审批链是独立事件表，应按 `expense_id` 批量关联，避免只读取最终审批节点。

- **风险评估**
  - **中高风险**：ID 映射错误可能把合法审批误判为自批。
  - 同名、离职人员、角色变更会造成历史数据误判。
  - 忽略代理审批会产生大量假阳性，应采用有效代理关系表和生效时间。

## 09. `expense / 09_large_low_level / large-amount-low-level-approval`

- **根因推测**
  - 金额阈值与审批等级规则未加载，或阈值配置键与代码读取键不一致。
  - 审批层级字段可能是文本、数字或权限等级，未做统一映射。
  - 金额使用了未标准化数值，或低级别审批事件没有关联到费用。
  - 大额规则可能被更高优先级异常短路。

- **修复方向**
  - 建立政策配置对象，统一定义：
    - 金额区间；
    - 币种；
    - 所需最低审批等级；
    - 允许的审批角色。
  - 金额统一转换为 `Decimal`/整数分后比较。
  - 对每笔费用获取有效审批链的最高有效审批等级；低于阈值即产生 finding。
  - 规则按多币种折算时使用指定汇率日期和汇率来源，并保留原币金额。

- **风险评估**
  - **高风险**：阈值、币种或汇率配置错误会大面积影响结论。
  - 多级并行审批、临时授权和先审批后补单可能造成误报。
  - 不应仅根据最终审批状态推断实际审批等级。

## 10. `expense / 10_cross_employee_invoice / cross-employee-invoice`

- **根因推测**
  - 规则可能只检查同一员工内部发票号重复，没有跨员工聚合。
  - 跨员工关联依赖员工字段，fixture 中可能使用了不同字段或姓名。
  - 聚合时只比较发票号，没有结合供应商税号，导致漏报或误报。
  - 组合 fixture 中其他规则先执行并中断流程。

- **修复方向**
  - 增加全表维度的重复发票检测，不按员工分片后再检测。
  - 按 `(supplier_tax_id, normalized_invoice_no)` 聚合，收集所有 employee key。
  - 组内出现两个及以上不同员工时输出 `cross-employee-invoice`。
  - 确保规则执行不依赖员工维度数据集，且不要因单条记录解析错误跳过整个聚合。
  - 单独员工维度的“员工+日期+金额”规则与跨员工发票规则分开。

- **风险评估**
  - **中高风险**：共享集团发票号、平台统一开票可能合法。
  - 仅按发票号、不结合供应商税号会误报。
  - 员工主键映射错误会把同一员工拆成多个身份。

## 11. `expense / 11_missing_expense_type / missing-expense-type`

- **根因推测**
  - 缺少必填字段校验，或校验结果只记录日志而未进入 findings。
  - 字段空值判断可能只认 `None`，未认 `""`、空白字符串及无效枚举值。
  - 规则在 schema 校验阶段抛错后被跳过。

- **修复方向**
  - 增加字段完整性规则，统一识别：
    - `None`；
    - 空白字符串；
    - 占位值；
    - 字典/列表中的空值；
    - 不在允许枚举中的类型。
  - 对缺失 `expense_type` 输出 `missing-expense-type`，并保留记录 ID。
  - 数据质量异常与业务违规分层输出，避免因字段缺失中止整个审计任务。
  - 在规则执行器中增加异常隔离：单条坏数据不能终止其他规则。

- **风险评估**
  - **低风险**：误报主要来自占位值或系统默认值的定义不一致。
  - 过度严格的枚举校验可能把新费用类型误判为非法。
  - 不应因一个字段缺失而阻断其他可计算规则。

## 12. `expense / 13_space_time_conflict / space-time-conflict`

- **根因推测**
  - 该规则可能根本未接入 `expense-audit`，或只存在于其他审计脚本。
  - 空间冲突可能需要地点资源/预约表，而费用脚本只读取费用数据。
  - 时间区间解析失败，或同名地点没有统一地点 ID。
  - 冲突判断只按员工，没有按“员工 + 地点资源”关联。

- **修复方向**
  - 在 `scripts/run_expense_audit.py` 中补充 `space-time-conflict` 规则，或将规则抽到公共模块后由两个入口共享。
  - 明确冲突资源主键：地点 ID、会议室 ID、车辆 ID 或差旅资源 ID。
  - 将开始/结束时间解析为带时区的 `datetime`，采用半开区间 `[start, end)` 判断重叠。
  - 同一时间范围、同一资源、不同员工即产生冲突；边界相接不算冲突。
  - 在结果中附冲突双方费用/预订 ID，便于复核。

- **风险评估**
  - **中风险**：同名地点、时区差异、全天事件和资源预订粒度不一致会造成误报。
  - 若规则仅存在于费用表而缺少资源占用数据，仍无法可靠判断。
  - 不宜仅凭相同地点文本判定冲突，应使用稳定资源 ID。

## 13. `expense / 14_cross_period / cross-period`

- **根因推测**
  - 未比较费用发生期间与审批、记账或支付期间。
  - “期间”可能被存为 `YYYY-MM`、`YYYYMM` 或起止日期，代码只支持一种格式。
  - 跨期只在单一周期内检查，未做费用与审批事件的跨周期关联。
  - 日期只按自然月判断，但 fixture 实际指财年季度或会计期间。

- **修复方向**
  - 引入会计日历配置，明确 period 类型：自然月、财月、季度或自定义结账周期。
  - 统一期间键，例如 `(fiscal_year, fiscal_period)`，不要只比较月份字符串。
  - 比较费用期间与审批/记账/支付期间；跨期则输出 `cross-period`。
  - 支持边界日期、期末调整和跨年期间。
  - 在结果中标明两个期间及所用日历版本。

- **风险评估**
  - **中高风险**：财年定义错误会使所有期间计算偏移。
  - 合理的跨月差旅、预付款、跨期结算可能合法。
  - 必须使用业务日历，而非简单月份截断。

## 14. `expense / 15_high_frequency_small_amount / high-frequency-small-amount`

- **根因推测**
  - 缺少频率聚合规则，或阈值/时间窗口配置未生效。
  - 计数在员工分片内进行，未跨商户或跨渠道聚合。
  - 时间窗口按自然日，而 fixture 期待滚动窗口；小时间戳差异导致漏报。
  - 小额阈值、频率阈值与币种换算不一致。

- **修复方向**
  - 增加滚动窗口聚合，例如按：
    - 员工；
    - 可选商户/费用类型；
    - 固定宽度时间桶或滑动窗口。
  - 对窗口内记录数和小额记录比例分别判断，命中后输出 `high-frequency-small-amount`。
  - 阈值应配置化，并记录命中的窗口、计数和金额。
  - 明确是否允许测试、差旅拆分支付等合法高频场景。

- **风险评估**
  - **中高风险**：窗口过短或忽略交易类型会误报。
  - 窗口过宽、阈值过高会漏报。
  - 时间戳精度和时区会影响边界计数，建议固定测试时钟。

## 15. `expense / 26_field_sales_precision / cross-employee-invoice`

- **根因推测**
  - 与案例 10 同源，但该 fixture 更强调现场销售和字段精度，代码可能对字段进行截断或错误归一化。
  - 跨员工关联键可能被映射到部门、门店或区域，而不是员工主键。
  - 同一发票可能因金额精度、税率或发票号格式差异未聚合。

- **修复方向**
  - 复用跨员工发票聚合组件，不为该 fixture 单独硬编码。
  - 员工维度应使用权威员工 ID，并保留组织层级作为辅助信息。
