# Expense Skill 失败案例审计报告

> 说明：当前仅提供了失败列表和 Skill 的脚本结构，未提供 `run_expense_audit.py`、规则配置、fixture 样本及实际运行日志。因此以下根因均属于**基于命名与失败类型的高概率推断**，应通过代码审查和 fixture 回放验证。  
> 列表实际包含 **38 条失败记录**，并非 11 条；下文按每条记录编号逐一列出。

## 共性判断

这些失败全部是 `false_negative`，且全部集中在 `expense`。这通常不像是单个规则的偶发失效，更可能存在以下全局问题之一：

1. **规则根本未执行**：expense 审计入口未加载、过滤条件写错，或结果未写回最终 finding。
2. **字段映射不一致**：脚本字段名与 fixture/规则字段名不同，例如 `invoice_date/date/txn_date`、`employee_id/employee/applicant_id`。
3. **时间处理错误**：日期被当作字符串，假期、周末、未来日期、跨期规则没有统一归一化。
4. **比较维度错误**：金额、员工、审批人或供应商的比较使用了错误对象，或只比较了单个字段。
5. **策略阈值未加载**：硬编码阈值、配置路径错误、字符串与数值比较，导致 `policy-threshold` 全部漏报。
6. **finding 类型不一致**：实际生成的是 `duplicate_invoice`、`weekend_expense` 等标签，而测试期望 `exact-duplicate-invoice`、`weekend-signal`。
7. **复合案例只返回首个 finding**：复杂场景中检测到了部分风险，但执行提前返回或结果被覆盖。

建议优先检查：

```python
# scripts/run_expense_audit.py
# 1. 规则是否注册并执行
# 2. 每个规则是否收集 finding，而非遇到异常后退出
# 3. finding["type"] 是否做统一映射
# 4. 日期、员工、审批人、金额是否使用规范化字段
# 5. 阈值是否从 policy 配置加载
```

## 1. `expense / 01_duplicate_invoice / exact-duplicate-invoice`

### 根因推测

重复发票检测可能使用了不稳定键，或只按发票号比较，导致完全重复的记录未命中：

- 比较键只包含 `invoice_number`，忽略了金额、日期、供应商等字段。
- key 中混入 `record_id`、`line_id`，使本应相同的记录产生不同键。
- 发票号字段映射错误，如读取 `invoice_id`，fixture 使用 `invoice_number`。
- 规则只标记第二、第三条，没有把重复组中每一条都加入 finding。
- 精确匹配前未做空白、大小写、全半角归一化。

### 修复方向

在重复检测前构造规范化业务键：

```python
def normalize_invoice_number(value):
    return re.sub(r"\s+", "", str(value or "")).upper()

duplicate_key = (
    normalize_invoice_number(row.get("invoice_number")),
    normalize_amount(row.get("amount")),
    normalize_date(row.get("expense_date")),
    normalize_text(row.get("vendor")),
)

groups = group_by(rows, duplicate_key)

for key, group in groups.items():
    if len(group) > 1:
        for row in group:
            findings.append({
                "type": "exact-duplicate-invoice",
                "record_id": row["id"],
                "duplicate_of": [r["id"] for r in group if r["id"] != row["id"]],
            })
```

若产品定义要求“完全相同的所有字段”，应使用规范化后的整行指纹；若是“同发票号重复报销”，则使用发票号主键加一致性校验，不能混淆两种语义。

### 风险评估

- **误报风险：中高**。供应商字段为空或格式差异大，可能把同一发票拆成不同 key。
- **漏报风险：中**。若严格使用所有字段，会漏掉同发票号的轻微变体。
- 建议区分 `exact-duplicate-invoice` 与 `near-duplicate`，不要共用一个模糊匹配规则。

## 2. `expense / 02_employee_date_amount / exact-duplicate-employee-date-amount`

### 根因推测

“员工 + 日期 + 金额”复合重复键没有正确构造：

- 员工字段读取错误，例如使用 `employee_name`，实际数据为 `employee_id`。
- 日期包含时区或时间戳，未转换到 `YYYY-MM-DD`。
- 金额是 `Decimal`、字符串或带货币符号，hash 值不一致。
- 规则键遗漏员工，或只比较了日期与金额。
- 按整张报销单分组，而非按费用明细行分组。

### 修复方向

确保比较发生在**明细行级**：

```python
def normalized_amount(value):
    return Decimal(str(value).replace(",", "").replace("$", "").strip())

def normalized_day(value):
    return parse_date(value).date().isoformat()

key = (
    str(row.get("employee_id")).strip(),
    normalized_day(row.get("expense_date")),
    normalized_amount(row.get("amount")),
)
```

同时增加空值保护：员工、日期或金额缺失时不应归为“精确重复”，应交给字段完整性规则处理。

### 风险评估

- **误报风险：中**。同一天同金额可能发生两笔真实消费。
- **误报风险：中低**。员工同日同金额的正常多笔消费确实常见。
- 建议额外加入供应商、费用类型、发票号，以区分业务重复与合理重复。

## 3. `expense / 03_sequential_invoices / sequential-invoice`

### 根因推测

可能未实现连续发票号检测，或排序方式错误：

- 发票号按字符串排序，导致 `"INV-10"` 排在 `"INV-2"` 前后异常。
- 没有处理前缀和数字部分。
- 只检测完全连续，没有考虑固定步长或允许间隔。
- 排序键包含日期，导致同号段无法聚类。
- 检测阈值未配置。

### 修复方向

提取发票号中的数值段并分组排序：

```python
def invoice_sequence_parts(value):
    match = re.fullmatch(r"([A-Za-z_-]*)(\d+)([A-Za-z_-]*)", str(value))
    if not match:
        return None
    return match.group(1).upper(), int(match.group(2)), match.group(3).upper()

for prefix, items in group_by(invoice_rows, lambda r: invoice_sequence_parts(r["invoice_number"])[:2]):
    items.sort(key=lambda r: invoice_sequence_parts(r["invoice_number"])[1])

    for previous, current in pairwise(items):
        if current_number - previous_number == 1:
            findings.append({
                "type": "sequential-invoice",
                "record_ids": [previous["id"], current["id"]],
            })
```

需明确连续定义：严格差值 1，还是允许少量缺号；是否限制日期、员工或供应商范围。

### 风险评估

- **误报风险：高**。正常连续开票非常常见。
- **风险控制**：仅在同供应商、同员工、短期内或金额模式相似时升级。
- 若只输出信号而非违规结论，误报影响较低。

## 4. `expense / 04_format_anomaly / invoice-format-anomaly`

### 根因推测

发票格式校验规则缺失、被异常捕获吞掉，或正则与 fixture 规范不一致：

- 正则只支持一种前缀、长度或日期格式。
- 未处理空格、连字符、大小写、全半角。
- 校验发生在字段缺失时抛异常，整个规则提前终止。
- 正则转义错误，例如 `\-`、`\d` 使用不完整。
- 实际字段是 `invoice_no`，代码读取 `invoice_number`。

### 修复方向

将格式规则配置化，并明确字段缺失和格式错误的不同结果：

```python
INVOICE_PATTERN = re.compile(r"^[A-Z]{2,5}-\d{4,12}$")

raw = row.get("invoice_number")
if raw is None:
    findings.append({"type": "missing-invoice-number", ...})
elif not normalize_invoice_number(raw) or not INVOICE_PATTERN.fullmatch(
    normalize_invoice_number(raw)
):
    findings.append({"type": "invoice-format-anomaly", ...})
```

增加单元测试覆盖：

- 合法格式；
- 大小写与空格；
- 非法字符；
- 空值；
- 超长编号；
- 不同国家或供应商的不同格式。

### 风险评估

- **误报风险：高**。不同组织、地区和供应商格式可能不同。
- **维护风险：中**。硬编码正则容易随业务变化失效。
- 建议采用“组织级白名单 + 基础格式合法性”，不要强制单一模板。

## 5. `expense / 05_holiday / holiday-signal`

### 根因推测

节假日信号依赖日历数据，但加载或匹配失败：

- 未加载节假日日历，或使用了不存在的路径。
- 节假日日期格式不一致。
- 规则按周末处理，遗漏法定节假日。
- 日期解析使用 UTC，转换后偏移一天。
- fixture 日期没有匹配当前节假日表版本。
- 异常被通用 `except` 吞掉，导致后续所有规则不执行。

### 修复方向

建立统一的节假日解析函数，并显式处理缺失日历：

```python
def load_holiday_dates(path):
    try:
        with open(path, encoding="utf-8") as f:
            payload = json.load(f)
        return {
            parse_date(item["date"]).date()
            for item in payload["holidays"]
        }
    except (OSError, ValueError, KeyError) as exc:
        logger.exception("holiday calendar unavailable: %s", exc)
        raise AuditConfigurationError("holiday calendar unavailable") from exc

if expense_day in holiday_dates:
    findings.append({
        "type": "holiday-signal",
        "record_id": row["id"],
        "date": expense_day.isoformat(),
    })
```

不能把“日历加载失败”静默当成“无节假日”。

### 风险评估

- **误报风险：中低**，前提是日历版本和地区正确。
- **漏报风险：高**。节假日表未更新会持续漏报。
- 建议记录数据版本、地区和最后更新时间。

## 6. `expense / 06_submit_before_expense / submit-before-expense`

### 根因推测

提交时间与费用发生时间比较字段错误或单位混乱：

- 使用了 `created_at` 与 `expense_date` 比较，而非 `submitted_at`。
- 一个字段是日期，另一个是时间戳。
- 字符串比较在标准日期格式下可能工作，但非补零格式会失效。
- 时区转换导致边界值误判。
- 提交时间解析失败后跳过了记录。
- 规则要求“早于费用日期”，但业务定义可能允许同一天。

### 修复方向

统一转换为带时区的 `datetime`，明确比较边界：

```python
expense_at = parse_datetime(row["expense_at"])
submitted_at = parse_datetime(row["submitted_at"])

if submitted_at < expense_at:
    findings.append({
        "type": "submit-before-expense",
        "record_id": row["id"],
        "delta": submitted_at - expense_at,
    })
```

如果业务只关心自然日：

```python
if submitted_at.date() < expense_at.date():
```

不要同时存在两套未文档化的语义。

### 风险评估

- **误报风险：中**。补录、离线审批和系统导入可能造成提交时间早于费用发生时间。
- **误报风险：中高**。时区或字段含义错误会造成系统性误报。
- 建议增加合理例外配置。

## 7. `expense / 07_future_date / future-date`

### 根因推测

未来日期比较依赖“当前时间”，但实现可能：

- 将费用日期与 `datetime.now()` 的字符串直接比较。
- 时区不一致。
- 使用 UTC 日期，而业务使用本地日期。
- 没有考虑未来报销周期或计划消费。
- `parse_date` 失败后直接 `continue`。
- 基准时间来自 fixture 未注入，导致不可复现。

### 修复方向

将审计基准时间作为参数注入，并统一时区：

```python
def audit(rows, now=None, business_timezone="Asia/Shanghai"):
    audit_now = ensure_aware(now or datetime.now(ZoneInfo(business_timezone)))
    local_today = audit_now.date()

    for row in rows:
        expense_day = parse_date(row["expense_date"]).date()
        if expense_day > local_today:
            findings.append({
                "type": "future-date",
                "record_id": row["id"],
                "expense_date": expense_day.isoformat(),
            })
```

在 fixture 中固定 `now`，避免测试随日期变化。

### 风险评估

- **误报风险：中**。预订未来酒店、机票或年费可能合法。
- **漏报风险：中**。时区及系统时间异常会影响结果。
- 建议将未来日期定义为信号，并允许政策例外。

## 8. `expense / 08_self_approval / self-approval`

### 根因推测

申请人与审批人比较使用了不一致的实体：

- 申请人是姓名，审批人是工号。
- 字段读取成 `approver_id` 与 `employee_name`。
- 代理审批、组织层级审批等关系未建模。
- 同一人的不同 ID 表示未归一化。
- 空值比较逻辑错误，例如两个空值被判为同一人。

### 修复方向

统一比较稳定员工标识：

```python
applicant_id = canonical_employee_id(row.get("employee_id"))
approver_id = canonical_employee_id(row.get("approver_id"))

if applicant_id and approver_id and applicant_id == approver_id:
    findings.append({
        "type": "self-approval",
        "record_id": row["id"],
        "employee_id": applicant_id,
    })
```

若需要覆盖代理审批，应查询审批关系或允许策略例外，而不是仅做字符串相等。

### 风险评估

- **误报风险：中高**。代理审批、老板共享账号、系统自动审批可能看似自批。
- **漏报风险：高**。姓名、员工 ID 或外部 HR ID 映射不一致会漏报。
- 不应在 ID 缺失时用姓名字符串兜底并直接判违规。

## 9. `expense / 09_large_low_level / large-amount-low-level-approval`

### 根因推测

大额低级别审批规则未生效：

- 阈值配置未加载或与比较对象类型不一致。
- 审批层级字段读取错误，例如 `approver_level` 与 `approval_level`。
- 层级排序方向写反，数字越小反而被判定更高。
- 金额包含税费、币种，未换算统一币种。
- 大额规则被其他 `if/elif` 分支遮挡。
- 只检查最终审批人，没有检查完整审批链。

### 修复方向

将阈值和层级映射显式配置：

```python
amount = convert_currency(row["amount"], row.get("currency"), "CNY")
minimum_level = policy["large_amount_min_level"]

if amount >= policy["large_amount_threshold"] and approval_level_of(row) < minimum_level:
    findings.append({
        "type": "large-amount-low-level-approval",
        "record_id": row["id"],
        "amount": amount,
        "approval_level": approval_level_of(row),
    })
```

`approval_level_of` 应基于角色权限表或组织层级数据计算，不能依赖可被用户输入的文本字段。

### 风险评估

- **误报风险：高**。汇率、税费及金额口径差异会改变阈值判断。
- **误报风险：中**。多层会签可能整体达到所需层级。
- 建议输出“实际审批链”和“要求层级”，便于人工复核。

## 10. `expense / 10_cross_employee_invoice / cross-employee-invoice`

### 根因推测

跨员工共享发票检测可能：

- 只按发票号分组，没有识别不同员工。
- 员工字段名错误，或读取了部门经理而非报销人。
- 同发票号经过格式转换后 key 不一致。
- 只比较同一报销单，而非跨单据。
- 规则只输出重复组中的一条，导致期望记录缺失。
- fixture 中发票号存在空白、前缀或类型差异。

### 修复方向

先按规范化发票号聚合，再比较报销人集合：

```python
for invoice_key, group in group_by(rows, normalized_invoice_number).items():
    employee_ids = {
        canonical_employee_id(r.get("employee_id"))
        for r in group
        if canonical_employee_id(r.get("employee_id"))
    }

    if len(employee_ids) > 1:
        for row in group:
            findings.append({
                "type": "cross-employee-invoice",
                "record_id": row["id"],
                "invoice_number": invoice_key,
                "employee_ids": sorted(employee_ids),
            })
```

同时决定是否把 `near-duplicate` 或供应商金额日期的相似发票纳入同一规则。

### 风险评估

- **误报风险：中**。集团内集中代报销可能合法。
- **漏报风险：高**。发票号轻微变化会直接漏报。
- 可增加供应商、金额、日期窗口做近似关联，但需避免与精确重复规则混用。

## 11. `expense / 11_missing_expense_type / missing-expense-type`

### 根因推测

必填字段检查可能未覆盖该字段，或对空值判定不正确：

- 只检查 `None`，未处理 `""`、空格、`"null"`、`"N/A"`。
- 字段名错误，例如规则使用 `category`，fixture 为 `expense_type`。
- 规则生成类型为 `missing-field`，期望为 `missing-expense-type`。
- 缺失值在数据清洗阶段被填成 `"Unknown"`，绕过了检查。
- 规则异常被前面的重复检测中断。

### 修复方向

统一缺失值判断并保留原始值：

```python
MISSING = {"", "null", "none", "n/a", "na", "unknown"}

def is_missing(value):
    return value is None or normalize_text(value).lower() in MISSING

if is_missing(row.get("expense_type")):
    findings.append({
        "type": "missing-expense-type",
        "record_id": row["id"],
        "field": "expense_type",
    })
```

不要在校验前把缺失值替换成 `"Unknown"`；如数据清洗必须填充，应同时保留 `missing_fields` 标记。

### 风险评估

- **误报风险：低**。
- **误报风险：中低**。某些系统确实
