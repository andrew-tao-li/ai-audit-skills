> **分析范围**：11 个失败案例，覆盖 expense-audit (7) 与 procurement-fraud (4) 两个 Skill
> **核心问题**：误报 (FP) 主导（7 例），表明检测规则的精确率（Precision）比召回率（Recall）更需优先优化

## 失败 #1

| 字段 | 值 |
|---|---|
| **Skill** | expense-audit |
| **Fixture** | complex_01_full_audit |
| **类型** | false_positive |
| **Detail** | split-expense |

### 根因推测
`run_expense_audit.py` 中的 `split-expense` 检测器很可能基于**单一维度**做拆分判定，例如：
- 仅按"金额阈值"切分（如：将 1 笔 9000 元报销按 >8000 阈值回溯，发现附近存在 2 笔 4500 元），未做**业务合理性验证**。
- 检测窗口可能硬编码（如 `WINDOW_DAYS = 7`），未考虑差旅/项目周期等长周期报销的天然聚合特性。
- **最可能位置**：`detect_split_expense()` 函数中，缺少 `is_likely_genuine_grouped_expense()` 二次过滤。

### 修复方向
```python
# 在 detect_split_expense() 末尾增加白名单校验
def is_genuine_grouping(txn_group):
    # 同项目、同出差申请单号、同费用类型、同部门
    return (same_project_id(txn_group) 
            and same_travel_request(txn_group)
            and txn_group.span_days <= project_duration)

flagged = [g for g in candidates if not is_genuine_grouping(g)]
```
同时建议将窗口期与"出差申请单"绑定，而非全局固定天数。

### 风险评估
| 风险项 | 等级 | 说明 |
|---|---|---|
| 漏报真实拆分报销 | 🟡 中 | 若白名单条件过宽，会放过真实舞弊 |
| 性能下降 | 🟢 低 | 增加 1 次 DB JOIN，可接受 |
| 误伤新业务 | 🟡 中 | 需补充未维护 project_id 的兜底分支 |

## 失败 #2

| 字段 | 值 |
|---|---|
| **Skill** | expense-audit |
| **Fixture** | complex_02_procurement_abuse |
| **类型** | false_positive |
| **Detail** | robust-outlier |

### 根因推测
该 fixture 名带 `procurement_abuse`，意味着被检测的交易可能实际上是**采购相关的高额支出**（如设备、原材料），却被 expense-audit 的 robust outlier 检测器（基于 Z-score / MAD / IQR）误判为异常报销。
- 根因：**检测器没有按 `expense_category` 分桶**，导致采购大额支出污染了普通报销的统计分布。
- 可能位置：`detect_outliers()` 中使用全局 median/MAD，未按 `category` 分组。

### 修复方向
```python
def detect_robust_outliers(txns):
    flagged = []
    for category, group in txns.groupby('expense_category'):
        # 分桶后再做 robust 检测
        local_flagged = iqr_outlier(group)
        flagged.extend(local_flagged)
    return flagged
```
并在判定阈值上，针对"采购类"使用更宽松的 multiplier（如 3.5 vs 默认 1.5）。

### 风险评估
| 风险项 | 等级 | 说明 |
|---|---|---|
| 小样本类别失效 | 🟡 中 | 某些 category 样本 < 5 时 MAD 不稳定，需 fallback 到全局阈值 |
| 规则漂移 | 🟢 低 | 仅影响 outlier 子模块 |

## 失败 #3

| 字段 | 值 |
|---|---|
| **Skill** | expense-audit |
| **Fixture** | complex_02_procurement_abuse |
| **类型** | false_positive |
| **Detail** | sequential-invoice |

### 根因推测
`sequential-invoice` 检测器可能在匹配"发票号码连续"时，将**同一供应商的合法连续开票**误判为虚假交易。
- 根因：检测器仅校验 `invoice_no` 连续性，未联合校验：
  - 金额是否合理（真实业务可能金额递增）
  - 供应商开票习惯（部分 ERP 系统自动生成连续号）
  - 业务单据（PO、收货单）是否齐全
- 可能位置：`detect_sequential_invoice()` 中的 `is_suspicious()` 判定函数过于宽松。

### 修复方向
增加多维佐证校验：
```python
def is_truly_sequential_fraud(group):
    has_continuous_no = check_continuous_invoice_no(group)
    has_po_mismatch = not all(has_matching_po(t) for t in group)
    has_receipt_gap = check_receipt_consistency(group) < 0.8
    return has_continuous_no and (has_po_mismatch or has_receipt_gap)
```
并引入供应商白名单机制，对"已知连续开票供应商"（如大型连锁）跳过检测。

### 风险评估
| 风险项 | 等级 | 说明 |
|---|---|---|
| 真实舞弊漏报 | 🟠 中高 | 真实连续号舞弊若同时伪造 PO，会漏掉 |
| 维护成本 | 🟡 中 | 供应商白名单需人工维护 |
| 误伤合法业务 | 🟢 低 | 多维校验后误报下降 |

## 失败 #4

| 字段 | 值 |
|---|---|
| **Skill** | expense-audit |
| **Fixture** | complex_02_procurement_abuse |
| **类型** | false_negative |
| **Detail** | near-duplicate |

### 根因推测
这是本批**唯一的 expense FN**，且与 #3（FP sequential-invoice）出现在同一 fixture → 强烈暗示该 fixture 中的交易**既是 sequential 又是 near-duplicate**，而 near-duplicate 检测未命中。
- 根因推测：
  1. `near-duplicate` 可能使用**精确金额匹配**，但真实舞弊会做 ±1% 微调（经典规避手段）。
  2. 检测窗口太窄（如默认 30 天），跨月规避未覆盖。
  3. 字段哈希只用了 `(amount, date)`，缺少 `description` 的语义相似度（"办公用品"/"文具"/"耗材"实为同类）。
- 可能位置：`detect_near_duplicate()` 中的 `similarity_threshold` 与字段集。

### 修复方向
```python
def detect_near_duplicate(txns, window_days=90):
    # 1. 金额容差 ±2%
    # 2. 字段: amount±tol, vendor, description_embedding, date in window
    # 3. description 使用编辑距离或 jaccard > 0.7
    candidates = fuzzy_match(txns, 
                             amount_tol=0.02,
                             desc_sim='jaccard',
                             window=window_days)
    return filter_with_business_logic(candidates)
```
同时考虑升级为 MinHash/LSH 以保证性能。

### 风险评估
| 风险项 | 等级 | 说明 |
|---|---|---|
| 性能 | 🟠 中高 | fuzzy match 计算量上升，建议加 LSH |
| 误报上升 | 🟡 中 | 容差放宽必然带来 FP，需配合业务校验 |
| 误伤相似但合规 | 🟡 中 | 真实业务中也存在相似描述，需 description embedding |

## 失败 #5

| 字段 | 值 |
|---|---|
| **Skill** | expense-audit |
| **Fixture** | complex_03_hr_falsified |
| **类型** | false_positive |
| **Detail** | exact-duplicate-invoice |

### 根因推测
"HR-falsified" 暗示此 fixture 包含 HR 部门**真实的多人差旅/培训报销**（不同员工使用同一培训机构开的相同金额发票，是合法场景）。
- 根因：`exact-duplicate-invoice` 检测器**只比对发票号，不区分报销人**。
- 真实场景：5 名员工参加同一培训，每人报销，发票号可相同（如团购开票）。
- 可能位置：`detect_exact_duplicate_invoice()` 中缺少 `employee_id` 的分组逻辑。

### 修复方向
```python
def detect_exact_duplicate_invoice(txns):
    dup_keys = txns.groupby('invoice_no').filter(lambda g: len(g) > 1)
    
    # 关键：同发票号但不同员工，且均关联同一业务事件 → 合法
    legit = dup_keys.groupby('invoice_no').filter(
        lambda g: g['employee_id'].nunique() > 1 
                   and g['event_id'].nunique() == 1
    )
    
    suspicious = dup_keys.drop(legit.index)
    return suspicious
```
需引入 `event_id`（培训ID/项目ID/出差申请单）作为白名单锚点。

### 风险评估
| 风险项 | 等级 | 说明 |
|---|---|---|
| 真实舞弊漏报 | 🟠 中高 | 同一员工重复报销同一发票号仍应被捕获——逻辑已正确（group 只有一个 employee_id） |
| event_id 缺失 | 🟡 中 | 老数据无 event_id 字段，需 backfill 或 fallback |
| 性能 | 🟢 低 | 仅增加 groupby 维度 |

## 失败 #6

| 字段 | 值 |
|---|---|
| **Skill** | expense-audit |
| **Fixture** | complex_03_hr_falsified |
| **类型** | false_positive |
| **Detail** | policy-threshold |

### 根因推测
policy-threshold（费用政策阈值）检测器将**合规的临界值报销**判定为违规。
- 推测场景：HR 政策规定"招待费单笔 ≤ 2000 元"，某员工报销 1999 元 → 被标为"接近阈值"可疑。
- 根因：
  1. 阈值检测使用了硬编码常量，未读取最新的 `policy_config` 表。
  2. 缺少"合理临界值"容差（typical practice: ±5% buffer）。
  3. HR 部门的特殊额度未生效（HR 招聘季可能临时放宽招待额度）。

### 修复方向
```python
class PolicyThresholdDetector:
    def __init__(self, policy_loader):
        self.loader = policy_loader  # 从 policy_config 表动态加载
    
    def check(self, txn):
        threshold = self.loader.get_threshold(
            txn.category, txn.department, txn.date
        )
        warning_band = threshold * 0.05  # 5% 警告带
        if threshold - warning_band <= txn.amount <= threshold:
            return None  # 临界值放行
        if txn.amount > threshold:
            return Violation(...)
        return None
```
配置改为热加载而非启动时缓存。

### 风险评估
| 风险项 | 等级 | 说明 |
|---|---|---|
| 配置变更延迟 | 🟢 低 | 改为每次查询 |
| 漏报真实超标 | 🟢 低 | 仅放宽 5% 边界 |
| 多部门策略冲突 | 🟡 中 | 需确保 policy_loader 优先级正确 |

| **Fixture** | complex_03_hr_falsified |
| **类型** | false_positive |
| **Detail** | submit-before-expense |

### 根因推测
"提交时间早于费用发生时间"——但**合法的预付/垫付场景**正是反向的：
- 员工提前垫付（如预订机票、缴付会议费），报销单在费用入账前提交完全合规。
- 根因：检测器未区分 `txn_type`（actual vs prepaid），且未读取 `expense_occurred_at` vs `submitted_at` 的业务语义。
- 可能位置：`detect_submit_before_expense()` 缺少 `txn_type` 过滤。

### 修复方向
```python
def detect_submit_before_expense(txns):
    flagged = txns[txns['submitted_at'] < txns['expense_occurred_at']]
    # 关键：预付类合法放行
    flagged = flagged[flagged['txn_type'] != 'prepaid']
    # 关键：垫付类需校验垫付审批单
    prepaid = flagged[flagged['txn_type'] == 'prepaid']
    prepaid_valid = prepaid[prepaid.has_prepay_approval]
    flagged = flagged.drop(prepaid_valid.index)
    return flagged
```

### 风险评估
| 风险项 | 等级 | 说明 |
|---|---|---|
| 真实违规漏报 | 🟢 低 | 规则更精细，捕获更准 |
| 表结构依赖 | 🟡 中 | 需 `txn_type`、`prepay_approval` 字段已落库 |
| 业务流程变更 | 🟢 低 | 仅扩展规则 |

```python
def detect_split_order(pos):
    candidates = group_recent_pos(pos, days=7)
    
    def is_legit(group):

    return [g for g in candidates if not is_legit(g)]
```

## 失败 #9

| 字段 | 值 |
|---|---|
| **Skill** | procurement-fraud |
| **Fixture** | complex_01_ma_carton |
| **类型** | false_negative |
| **Detail** | price-outlier |

### 根因推测
与 #8 同一 fixture，#8 是 FP（业务合法被判违规），#9 是 FN（真实价格异常未捕获）→ 暗示该 fixture 中存在**价格操纵的隐蔽模式**。
- 推测真实舞弊模式：
  - 同一物料在多笔订单中**价格在小范围内持续上涨**（每次 +1~2%），未触发单笔 outlier，但累计涨幅显著。
  - 或价格与**市场价偏离**但与历史采购均价对齐（洗价）。
- 根因：`price-outlier` 仅做"单笔 vs 历史均值"的横截面比较，**缺少时序趋势检测**。

### 修复方向
引入时序异常检测：
```python
def detect_price_drift(material_id, lookback_months=12):
    history = get_price_history(material_id, months=lookback_months)
    
    # 1. 累计涨幅异常
    cumulative_change = (history[-1] - history[0]) / history[0]
    
    # 2. 局部趋势：CUSUM / Page-Hinkley
    cusum_alarm = cusum_detect(history)
    
    # 3. 市场价比对
    market_deviation = abs(history[-1] - market_price(material_id)) / market_price
    
    return any_flag(cumulative_change > 0.15, cusum_alarm, market_deviation > 0.1)
```

### 风险评估
| 风险项 | 等级 | 说明 |
|---|---|---|
| 市场数据源 | 🟠 中高 | 需引入第三方价格指数，可靠性存疑 |
| 季节性误报 | 🟡 中 | 原材料价格波动大，需考虑 STL 分解 |
| 计算复杂度 | 🟡 中 | CUSUM 需逐物料滚动计算 |

## 失败 #10

| 字段 | 值 |
|---|---|
| **Skill** | procurement-fraud |
| **Fixture** | complex_02_emergence |
| **类型** | false_positive |
| **Detail** | process-order-before-approval |

### 根因推测
"emergence"（应急采购）—— 该 fixture 模拟**真实的紧急采购场景**：
- 设备故障、生产停线时，采购先下 PO、后补审批是行业通行做法。
- 根因：
  1. `process-order-before-approval` 检测器未识别 `emergency_flag` 或 `urgent_procurement_reason`。
  2. 缺少"应急采购事后 24h 内补审"的合法窗口。
- 可能位置：`procurement_fraud.py::detect_order_before_approval()`。

### 修复方向
```python
def detect_order_before_approval(pos):
    suspicious = pos[pos['order_date'] < pos['approval_date']]
    
    # 应急采购白名单
    emergency = suspicious[
        (suspicious['emergency_flag'] == True) 
        & (suspicious['approval_lag_hours'] <= 24)
    ]
    
    # 合同/法务特殊通道
    legal_channel = suspicious[
        suspicious['approval_channel'] == 'fast_track_legal'
    ]
    
    return suspicious.drop(emergency.index).drop(legal_channel.index)
```
需采购系统补 `emergency_flag`、`approval_channel` 字段。

| 风险项 | 等级 | 说明 |
|---|---|---|
| 应急滥用 | 🟠 中高 | 若 emergency_flag 可被随意打上，规则失效——需审批环节复核 |
| 字段缺失 | 🟡 中 |
