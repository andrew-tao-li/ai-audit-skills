## 失败 #1：expense / split-expense（FP）

**现象**：`complex_01_full_audit` 全量审计中，把合法报销被拆分成多笔的行为判定为风险。

**根因推测**：
- `run_expense_audit.py` 中 split-expense 检测器大概率使用"同一提交人 + 同一日期 + 近似金额"作为拆分特征，但没有引入"业务合理性"白名单（如差旅分天、餐饮分日预算、跨币种分笔）。
- 检测函数可能直接用了 `abs(amount_i - amount_j) / max(amount_i, amount_j) < ε`，未结合 category、project_code、currency 等维度。
- 缺乏"分笔背景说明"字段（justification/note）的语义解析。

**修复方向**：
- 在 `detectors/split_expense.py` 中加入多维特征：必须满足 (a) 同 submitter 且同日 或 相邻日，(b) 缺少 note 字段或 note 为空，(c) 单笔均低于某阈值但合计超阈值，才告警。
- 增加 `policy_threshold` 上下文：拆分若符合公司差旅政策的日限额拆解，应自动白名单。
- 引入 `category` 分组：餐饮、住宿、交通各自独立判断，不跨类合并。

**风险评估**：🔴 **中等偏高**。若白名单规则过松，会漏掉真实拆分（如把一笔 5000 拆成 5×1000）。建议保留"可解释性"——所有白名单命中必须留下 audit_log 记录，便于人工复核。

## 失败 #2：expense / robust-outlier（FP）

**现象**：基于鲁棒统计（如 MAD / IQR）的离群点检测，在 procurement 滥用场景中误报。

**根因推测**：
- `run_expense_audit.py` 中 `robust_outlier()` 函数可能对**全局**金额分布计算 z-score 或 modified z-score，未按 `department` / `cost_center` / `expense_type` 分组。
- 采购类费用天然金额偏高（设备、原材料），若混在差旅分布里，MAD 会被高金额拉高，正常的差旅也可能被打成离群。
- 另外，fixture 名称 `procurement_abuse` 暗示该场景**应**被 expense 端捕获（可能通过发票号关联），但检测器只跑金额统计，没结合发票合规性。

**修复方向**：
- 在 `detectors/robust_outlier.py` 增加**分层**（stratified）计算：先按 `category` 聚合，再在每个 stratum 内做 MAD。
- 增加最小样本量检查：某 stratum 内样本 < 30 时不告警（样本不足统计无效）。
- 对 procurement-related expense，引导到 procurement skill 做二次判断（cross-skill handoff）。

**风险评估**：🟡 **中等**。分层后可能漏掉"跨类聚合"的舞弊（如同一提交人用不同类别）。需配合 case-level 聚合指标作为兜底。

## 失败 #3：expense / sequential-invoice（FP）

**现象**：把合法连续编号发票识别为异常连续序列。

**根因推测**：
- `detectors/sequential_invoice.py` 检测相邻发票号差值为 1 或递增小步长，但未考虑：
  - 同一供应商的正常连续开票（如办公用品月度采购）。
  - 跨月份/跨季度发票号跳号是常态。
- 可能用了纯字符串前缀匹配，未提取 numeric portion。
- 缺乏"提交人 ≠ 发票主体"的检查：若多笔发票是不同供应商提供，不应串联。

**修复方向**：
- 提取发票号 numeric 部分后，仅对"同一 vendor + 同一 submitter + 短时间内连号"告警。
- 增加连续号长度阈值（≥ 3 张才告警，且间隔天数 < N）。
- 加入 `vendor_variety` 维度：连号发票若分属 ≥ 2 个 vendor，告警降级为提示。

**风险评估**：🟢 **低**。这类规则收紧后，副作用主要是漏报少数"用真连号做掩饰"的舞弊，可由 near-duplicate 检测器补偿。

## 失败 #4：expense / near-duplicate（FN）🔴 **高危漏报**

**现象**：complex_02 中存在近似重复报销（金额相近、发票相似但不完全相同），未被检出。

**根因推测**：
- `detectors/near_duplicate.py` 当前仅比较**完全相同**的字段（如发票号），对以下情况失效：
  - 发票号被改动一位（OCR 错误 / 故意篡改）。
  - 金额四舍五入 ±1 元。
  - 日期相差 1-2 天。
- 相似度函数可能用 `exact_match` 而非 `fuzzy_match`（Levenshtein / Jaro-Winkler）。
- 阈值 `threshold=1.0`（全字段一致）过高。

**修复方向**：
- 改为多字段加权相似度：`0.5*sim(invoice_no) + 0.3*sim(amount) + 0.2*sim(date+vendor)`，阈值降至 0.85。
- 对 (submitter, vendor, amount_rounded) 建立倒排索引，快速召回候选对。
- 引入 SimHash / MinHash 用于批量近邻检索，支撑大规模场景。
- 注意：sim(amount) 使用相对差，金额 10000 和 10001 视为相同；金额 10 和 11 也视为相同——需要分段处理（小金额更敏感）。

**风险评估**：🔴 **高**。降低阈值必然带来 FP 上升（与案例 #1、#5 冲突）。建议：
- 引入"二阶段"：召回（高 recall，低 precision）→ 精排（人工可解释特征）。
- 输出 top-K 候选供调查助手（investigation-assistant）做人工复核。

## 失败 #5：expense / exact-duplicate-invoice（FP）

**现象**：complex_03_hr_falsified 中，HR 伪造报销里存在完全重复发票，但被 FP（这意味着把合法重复当成了异常，或者告警方向反了）。

**根因推测**：
- **情形 A**：检测器对**所有**完全重复发票告警，命中了合法场景（如同一笔费用先由公司卡垫付后个人卡还款，可能产生系统内重复记录）。
- **情形 B**：HR 伪造场景本应被 `exact-duplicate` 捕获，但当前实现未覆盖 HR 子系统特有字段（如 `employee_id` vs `employee_name`、HR 模块与财务模块数据 join 缺失）。
- 检测器可能只看 `expense` 表自身，未与 `hr_payroll` / `hr_contract` 做交叉验证。

**修复方向**：
- 在 `detectors/exact_duplicate.py` 中区分"系统内重复记录"（同一笔订单的多次记账）与"用户重复提交"（人工行为）。
- 增加 `source_system` 字段：来自 POS 自动记账 vs 人工上传应区别对待。
- 对 HR 类报销，必须 cross-skill 调用 `procurement-fraud` 或专门的 `hr-audit` 做交叉。

**风险评估**：🟡 **中等**。需要构建跨系统数据通道（expense ⇄ hr），治理成本不低。

## 失败 #6：expense / policy-threshold（FP）

**现象**：基于阈值（如单笔 500 上报、5000 重点关注）的策略被误报。

**根因推测**：
- `policy/threshold.yaml` 中硬编码了金额阈值，未考虑：
  - 不同部门预算差异（销售部差旅 vs 后勤采购）。
  - 不同地区的物价差异（一线城市 vs 海外）。
  - 季节性波动（Q4 采购高峰）。
- 像 `complex_03_hr_falsified` 场景下，HR 部门本身金额就低，阈值过严导致正常福利发放被误判。

**修复方向**：
- 阈值改为"动态阈值"：base × department_factor × region_factor × season_factor。
- 引入"绝对偏离度 + 相对偏离度"双指标：仅当同时超过历史均值 K 倍**且**超过绝对阈值才告警。
- 提供 admin UI 让审计师按部门微调阈值。

**风险评估**：🟢 **低-中**。动态阈值规则维护成本上升，但 FP 显著降低。

## 失败 #7：expense / submit-before-expense（FP）

**现象**：检测到"费用发生前提交报销"的时间逻辑异常，但实际场景下这是合法行为。

**根因推测**：
- `detectors/temporal.py` 检测 `submit_date < expense_date` 时，未考虑：
  - 预付卡 / 储值卡先充值后消费。
  - 跨境报销时区差异。
  - 报销系统日期与财务记账日期口径不同。
- 时间字段可能没有时区信息，全用 `datetime.date()` 比较。

**修复方向**：
- 引入 `expense_type` 白名单：预付类、储值类、月结类不触发此规则。
- 增加容差窗口：`submit_date < expense_date - 7 days` 才告警（轻微提前合理）。
- 对接业务系统获取"费用实际发生时间"而非"发票开具时间"。

**风险评估**：🟢 **低**。此规则即使放宽 7 天窗口，对真实"伪造报销"的捕获率影响有限（造假者不会精确控制日期）。

## 失败 #8：procurement / split-order（FP）

**现象**：把合法拆单（如年度框架协议下的多次按需下单）判为风险。

**根因推测**：
- `run_procurement_audit.py` 中 `split_order` 检测器与 expense 的 split-expense 类似，未关联：
  - PO 框架协议（master PO）下的 release order。
  - 项目阶段交付物（WBS 节点）。
  - 同一合同号下的合法分批。
- 可能缺少对 `parent_po_id` / `framework_agreement_id` 字段的读取。

**修复方向**：
- 引入 `contract_ref` / `framework_po` 字段 join；命中框架协议的 split 不告警，仅记入"信息项"。
- 拆分识别增加时间窗口约束：若拆单跨越 ≥ 30 天，可能是真实分批交付。
- 增加 `delivery_milestone` 关联。

**风险评估**：🟡 **中等**。修复需要打通合同管理系统数据。

## 失败 #9：procurement / price-outlier（FN）🔴 **高危漏报**

**现象**：complex_01_ma_carton（"妈" 纸箱？猜测为原材料采购）中存在价格异常（如单价虚高、串标），未被检出。

**根因推测**：
- `detectors/price_outlier.py` 可能仅做"内部对比"（与历史采购均价比），未做：
  - **外部市场行情对比**（需要市场数据 feed）。
  - **多供应商对比**（同一物料多家报价比对）。
  - **成分分析**（原材料涨价传导合理性）。
- 单位换算缺失：纸箱可能按"个"报价，原料按"kg"报价，若未做 UOM 归一化，价格比较失真。

**修复方向**：
- 接入外部价格基准（如大宗商品行情 API）。
- 对同类物料建立 vendor × item 的价格矩阵，计算相对偏离度。
- 加入 `unit_of_measure` 标准化层。
- 引入"价格异常 + 数量异常"复合条件：单一异常不告警，两者同时异常则升级。

**风险评估**：🔴 **高**。外部数据接入成本高，且市场行情本身有波动。建议先做"内部多供应商对比"，这是数据可得性最高的方案。

## 失败 #10：procurement / process-order-before-approval（FP）

**现象**：流程合规检查中，把"先下 PO 后审批"判为异常，但实际紧急采购（如生产停线）允许此模式。

**根因推测**：
- `detectors/process_compliance.py` 强制要求 `approval_date < po_date`，未识别 `emergency_procurement` flag / `expedited_approval` 后补流程。
- 紧急采购通常事后补批（post-approval），但当前规则只检查时间戳先后。

**修复方向**：
- 读取 `procurement_type` / `urgency_level` 字段，急采/特采允许先 PO 后批，但要求事后 N 天内补齐审批。
- 区分"先斩后奏但已补"与"完全绕过审批"。
- 增加补批时效检查：`po_date` 与 `approval_date` 间隔超 X 天才升级告警。

**风险评估**：🟡 **中等**。规则放宽后需配套"补批率"指标监控，防止系统性绕审。

---

## 失败 #11：procurement / process-receipt-before-approval（FN）🔴 **高危漏报**

**现象**：complex_02_emergence（紧急采购）中存在"收货早于审批"的严重合规问题，未被检出。

**根因推测**：
- 与 #10 共享 `detectors/process_compliance.py`，但代码只检查了 `po` 相关节点，未检查 `receipt`（收货 / 入库）。
- 或者 `receipt` 节点根本未进入检测 pipeline（数据源缺失）。
- 紧急采购场景下"先收货"是常见漏洞，攻击者利用此规则盲区。

**修复方向**：
- 扩展 `process_compliance` 至覆盖完整流程：requisition → approval → PO → receipt → invoice → payment。
- 引入"任意前置节点早于审批即告警"的通用规则，对紧急采购豁免时必须 `urgency=true AND justification != null`。
- 在 `build_case_workspace.py` 中，将该检测作为"必查项"列入 emergency 类 fixture。

**风险评估**：🟢 **低**。扩展检测节点是单向收益（增加告警面），只要白名单合理，不会显著增加 FP。

## 横向总结

### 共性根因
1. **缺乏上下文**：8/11 FP 都是"缺乏业务上下文"导致（白名单不足、字段未关联）。
2. **检测器过于局部**：近一半 FP 来自单一维度判断（金额 / 时间），未做 cross-field 联合推理。
3. **紧急 / 异常流程盲区**：#10、#11 共用同一检测器，反映 emergency flow 未被特殊建模。
4. **相似度算法过严**：#4（near-duplicate FN）是最严重漏报，根因是 exact match 而非 fuzzy。

### 优先修复排序
| 优先级 | 案例 | 理由 |
|--------|------|------|
| P0 | #4, #9, #11 | 高危漏报，直接造成资金损失 |
| P1 | #5, #10 | 合规盲区，可能引发监管风险 |
| P2 | #1, #2, #8 | FP 较多，影响审计师信任度 |
| P3 | #3, #6, #7 | 单点误报，影响有限 |

### 架构级建议
1. **引入规则上下文层（Rule Context Layer）**：所有检测器在判断前先收集 `department / contract / urgency / vendor_history` 等上下文。
2. **建立 cross-skill 协同**：expense 的 procurement 相关异常应自动委派给 procurement skill 二次判断。
3. **检测器版本化与 A/B 评估框架**：每个 detector 改动后，应在所有 fixture 集上跑回归，避免新规则引发其他案例 FP/FN。
4. **元数据驱动的白名单**：将白名单从代码中剥离，放入 YAML/DB 配置，支持运营自助调整。
