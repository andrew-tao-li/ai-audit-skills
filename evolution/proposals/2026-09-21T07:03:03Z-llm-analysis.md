# 失败案例根因分析与修复方案

---

## 失败 #1: expense / complex_01 / false_positive / split-expense

### 1. 根因推测
- `run_expense_audit.py` 中的"拆单检测"可能使用了**单维度金额阈值**（如单笔 < ¥5,000 即忽略），未结合**多维度特征**（如同一供应商、相近时间、相同报销人、累计金额超阈值）。
- Fixture `complex_01_full_audit` 通常模拟"业务招待费"分拆报销场景，代码若按 `amount < threshold` 直接放行，会将真实拆单漏判。

### 2. 修复方向
- 定位 `run_expense_audit.py` 中检测函数（约在 `detect_split_expense()` 或相似命名）。
- 引入 **滑动窗口聚合**：以 `vendor_id + employee_id + category` 为分组键，在 7 天 / 30 天窗口内累加金额，超过阈值才告警。
- 增加"金额接近度"特征（如单笔金额在 ±20% 区间），降低对单一指标的依赖。

### 3. 风险评估
- **性能风险**：滑动窗口聚合增加计算量，需评估数据量（<10 万行可全内存，>则需分桶或使用 SQLite 临时表）。
- **误报转移**：窗口和阈值调严可能把正常分批采购（如办公用品月度补货）误报，建议按 `category` 设置差异化阈值。

## 失败 #2: expense / complex_02 / false_positive / robust-outlier

### 1. 根因推测
- "稳健统计离群点检测"（如基于中位数 + 1.5×MAD 或 IQR）若**未按类别分组**，会因品类间金额差异（如办公用品 vs 设备采购）误报。
- `complex_02_procurement_abuse` 含大量高额采购，正常离群点被错判为异常。

### 2. 修复方向
- 在离群检测函数中强制要求 `groupby(category, vendor_type)` 后再做 MAD/IQR 计算。
- 增加 `min_group_size` 阈值（如 < 5 条不参与离群判定，避免小样本过拟合）。

### 3. 风险评估
- **样本不足**：部分小众品类样本 < 5 时不告警，可能漏掉真实异常——需配合"绝对金额阈值"作为兜底。
- **类别标注依赖**：若 category 字段为空或不一致（脏数据），分组后离群点消失；需先做数据清洗。

## 失败 #3: expense / complex_02 / false_positive / sequential-invoice

### 1. 根因推测
- "连续发票检测"（sequential invoice）若仅按 `invoice_number` 字典序连续判断，会把正常编码规则的发票（如 INV-001, INV-002, …）误判为伪造。
- 代码可能缺少"非连续发票号中夹杂跳号"的合理性校验。

### 2. 修复方向
- 在 `detect_sequential_invoice()` 中加入：
  - **前缀归一化**：提取数字部分后比较。
  - **数量阈值**：连续 ≥ N 张（N≥3 或 5）才告警。
  - **结合金额特征**：连续号 + 相近金额 + 同一供应商才标记高风险。

### 3. 风险评估
- **绕过成本低**：欺诈者可主动跳号规避，需结合"近似号 + 同供应商 + 同金额"组合规则。
- **国际化发票号格式复杂**（中文、字母混合），正则需谨慎设计。

## 失败 #4: expense / complex_02 / false_negative / near-duplicate

### 1. 根因推测（FN 更严重）
- "近重复检测"可能依赖**精确哈希**（MD5/SHA256）整张发票图，对"金额微调"（如 ¥1000 → ¥999）、"日期偏移"等近重复漏检。
- Fixture 中常见手法：同一发票只改 1 个字段（金额 ±1 元，或日期 ±1 天）。

### 2. 修复方向
- 实现**字段归一化 + 指纹 + SimHash**或**模糊哈希**（如 pdftotext + MinHash）。
- 关键字段（发票号、金额、供应商）单独对比，允许小偏差（如金额差 < 1% 且其他字段一致）。
- 推荐算法：
  ```
  similarity = (matched_fields / total_fields) * weight
  if similarity > 0.8 and amount_diff_ratio < 0.05: flag
  ```

### 3. 风险评估
- **计算开销大**：MinHash/模糊哈希对 N 张发票做 O(N²) 比较，10 万级数据需使用 LSH 索引（如 `datasketch`）。
- **阈值难调**：过低则误报增加，过高则漏报——需要标注集训练。

## 失败 #5: expense / complex_03 / false_positive / exact-duplicate-invoice

### 1. 根因推测
- 与 #4 对偶：精确去重逻辑只比对 `invoice_number`，若上游 ERP 系统允许多张报销单引用同一张发票（如差旅中机票多人均摊），会被错判。
- `complex_03_hr_falsified` 包含 HR 场景，可能存在"同一发票号对应多个报销单"的合理业务。

### 2. 修复方向
- 引入**业务场景白名单**：如机票、火车票、酒店可允许多人共用。
- 检测时应检查 `(invoice_number, employee_id)` 联合唯一性，单 invoice_number 重复不必然异常。

### 3. 风险评估
- **白名单维护成本**：需定期与业务确认可共用发票类型，否则会被利用逃避检测。
- **增加复杂度**：白名单逻辑易引入新 bug，建议用配置化（YAML）管理。

## 失败 #6: expense / complex_03 / false_positive / policy-threshold

### 1. 根因推测
- "政策阈值"检测可能用了**全局硬阈值**（如 ¥5,000 需审批），未考虑**审批豁免名单**（如高管、紧急采购）或**业务类型差异**（差旅 vs 招待）。
- Fixture `complex_03_hr_falsified` 中的合规金额被误判。

### 2. 修复方向
- 将阈值改为**配置文件驱动**：
  ```yaml
  thresholds:
    default: 5000
    by_category:
      travel: 10000
      entertainment: 2000
    by_role:
      executive: 20000
      emergency_override: true
  ```
- 检测函数读取 `config/policy.yaml`，按 employee_role 和 category 路由。

### 3. 风险评估
- **配置漂移**：政策文件更新滞后于真实业务规则，需建立配置审计流程。
- **过度灵活**：若阈值可被随意调高，会削弱审计能力——建议设置配置变更日志。

## 失败 #7: expense / complex_03 / false_positive / submit-before-expense

### 1. 根因推测
- "先提交后消费"检测可能按 `submit_date < expense_date` 字面判断，忽略了：
  - 时区差异（跨时区差几小时）
  - `submit_date` 字段为审批时间而非发起报销时间
  - 预付卡 / 信用卡入账延迟

### 2. 修复方向
- 增加**容差窗口**：如允许 1-3 天时差。
- 区分 `submit_date`（发起）与 `approve_date`（审批），只校验后者早于消费日期。
- 时区统一用 UTC 存储，渲染时按本地时区。

### 3. 风险评估
- **容差被利用**：欺诈者可利用 3 天容差套利，但相比误报可接受。
- **数据契约**：需确保上游系统明确字段语义，建议在数据字典中标注。

## 失败 #8: procurement / complex_01 / false_positive / split-order

### 1. 根因推测
- `run_procurement_audit.py` 的"拆单检测"可能仅看**单笔订单金额**，未做跨订单聚合。
- `complex_01_ma_carton`（纸箱采购）场景下，规模化采购常分批下单，正常业务被误判为拆单规避审批。

### 2. 修复方向
- 按 `(requester, supplier, material_category, time_window)` 分组聚合订单。
- 设定 `min_orders ≥ 3` 且累计金额超阈值才告警。
- 排除"标准 BOM 物料"或"框架协议下的分批交付"。

### 3. 风险评估
- **业务复杂度**：制造业常有周期性补货，需引入"框架订单"白名单。
- **跨月拆分**：时间窗口过短会漏掉跨月拆单，过长会增加误报——建议 30 天 + 可配置。

## 失败 #9: procurement / complex_01 / false_negative / price-outlier

### 1. 根因推测（FN 优先级最高）
- "价格离群"检测可能仅做**全局 IQR**，未考虑：
  - 不同供应商报价差异
  - 原材料市场价格波动
  - 规格 / 型号不同的同种物料
- `complex_01_ma_carton`（纸箱）受原材料价格影响大，单笔高价可能漏报。

### 2. 修复方向
- 严格按 `(material_id, supplier_id, spec_hash)` 三元组分组做统计。
- 引入**外部价格基准**（如大宗商品价格指数）作为参考。
- 增加**纵向趋势检测**：同一物料价格月环比 > 30% 单独告警。

### 3. 风险评估
- **外部数据依赖**：接入大宗商品数据增加复杂度与维护成本。
- **冷启动问题**：新物料无历史价格，离群检测失效——需在告警中标注"历史数据不足"。

## 失败 #10: procurement / complex_02 / false_positive / process-order-before-approval

### 1. 根因推测
- "未审批先下单"检测可能未区分：
  - **预审批**（框架协议下提前下单）
  - **紧急采购**（事后补审批）
  - **审批状态字段延迟更新**
- `complex_02_emergence`（紧急采购）场景中，紧急订单的审批可能在订单创建后才完成，属正常流程。

### 2. 修复方向
- 增加 `approval_status` 多值容忍：`approved`、`retroactively_approved`、`under_review`。
- 紧急采购走独立检测路径，结合"采购事由"字段（"紧急"关键词 + 高金额阈值）放行。
- 引入 SLA：紧急订单需在 24-72 小时内补齐审批，否则升级告警。

### 3. 风险评估
- **审批绕过风险**：被滥用为"所有采购都打紧急标签"，需配合抽检。
- **流程复杂度提升**：与 ERP 工作流耦合度增加，故障点增多。

## 失败 #11: procurement / complex_02 / false_negative / process-receipt-before-approval

### 1. 根因推测（FN）
- 与 #10 对偶："未审批先收货"告警可能被**抑制规则**压制。
- 代码可能在检测到"审批缺失"后，未在"已收货"环节再次拦截（通常系统中审批前不应允许入库）。
- 紧急采购场景下，收货节点未被纳入关键控制点检查。

### 2. 修复方向
- 在 `build_case_workspace.py` 调查中联动 `procurement` 检测：
  - 收货时间 < 审批完成时间 → 高优先级告警（违反"四眼原则"）
- 增加**控制矩阵**：订单创建 / 收货 / 付款三节点都校验审批状态。

### 3. 风险评估
- **告警疲劳**：三节点都查会大幅增加告警量，需配套告警分级（红/黄/蓝）。
- **数据一致性**：收货时间可能由仓储系统回写，存在时间戳精度问题（秒级 vs 毫秒级）。

# 总结性洞察

| 维度 | 观察 |
|------|------|
| **最高优先级** | FN 类（#4, #9, #11）——漏检真实欺诈，业务损失大 |
| **共性根因** | 多数 FP 源于**单一维度检测**未结合上下文（业务、类别、时间窗口） |
| **代码层建议** | 引入**配置化阈值**（policy.yaml）+ **分组聚合**（groupby）+ **白名单机制** |
| **架构层建议** | 将"检测规则"从脚本中解耦为 `rules/*.yml`，便于业务调优而无需改代码 |
| **测试建议** | 每个 fixture 应有**正向 + 反向 + 边界**三组用例，避免规则偏向一侧 |

建议优先修复 FN 三例，再处理 FP 误报，最后优化检测规则的配置化能力。
