# 审计 Skill 失败案例分析报告

> 涉及 Skill：`expense-audit`、`procurement-fraud`
> 分析维度：根因推测 → 修复方向 → 风险评估

## 二、逐条分析

### 失败 #1 — expense / split-expense / FP

**1. 根因推测**
`run_expense_audit.py` 中 `split-expense` 规则很可能按"同一员工 + 时间窗口内多笔小额"触发，但未校验这些小额是否属于**同一业务目的**（如同一差旅、同一项目）。complex_01 是完整审计场景，正常的多笔报销被误判为拆分。

**2. 修复方向**
- 在 `detect_split_expense()` 中增加**业务键聚合**：`(employee_id, project_code, cost_center, trip_id)`。
- 引入"合并后是否超过审批阈值"作为二次确认条件——只有拆分能规避审批才报。
- 增加白名单：同一 trip_id / 同一发票批次号内的多笔不触发。

**3. 风险评估**
- 收紧后可能漏掉"跨项目拆分"的隐蔽欺诈（FN 风险上升）。
- 需要 fixture 中提供 `trip_id`/`project_code` 字段，否则规则失效。
- 建议保留"低置信度"输出而非直接丢弃。

---

### 失败 #2 — expense / robust-outlier / FP

**1. 根因推测**
`robust-outlier` 使用 MAD 或 IQR 检测金额异常，但 complex_02 是采购滥用场景，**基线样本本身被污染**（大量异常值拉高分布），导致正常大额报销被误判为 outlier。

**2. 修复方向**
- 改用**分层基线**：按 `expense_category` + `department` 分组计算中位数/MAD。
- 引入**稳健估计**：使用 trimmed mean 或 Theil-Sen，避免污染样本影响。
- 增加最小样本量门槛（如 n<10 不触发 outlier）。

**3. 风险评估**
- 分层后小样本组统计不稳定，可能产生新的 FP。
- 若 fixture 中类别字段缺失，规则退化。
- 需回归测试确保原有真实 outlier 仍被捕获。

---

### 失败 #3 — expense / sequential-invoice / FP

**1. 根因推测**
`sequential-invoice` 检测连续发票号，但时间窗口设置过宽（如 30 天），把正常业务中供应商连续开票误判为异常。

**2. 修复方向**
- 缩短时间窗口至 **24–72 小时**（连续开票的典型欺诈特征）。
- 增加**金额相近性**约束（连续号 + 金额差异 <5% 才报）。
- 排除同一供应商同一合同的正常分期开票。

**3. 风险评估**
- 窗口过窄会漏掉"慢速拆分"欺诈（FN）。
- 金额约束可能被攻击者规避（故意改金额）。
- 建议输出为"可疑"而非"确认"。

---

### 失败 #4 — expense / near-duplicate / FN

**1. 根因推测**
`near-duplicate` 使用编辑距离或哈希相似度，阈值设得过高（如 0.95），complex_02 中的近似重复发票（金额微调、日期偏移）未被捕获。

**2. 修复方向**
- 降低相似度阈值至 **0.80–0.85**，并改用**多字段加权相似度**（供应商、金额、日期、描述）。
- 引入**模糊匹配**：金额允许 ±2% 浮动，日期允许 ±3 天。
- 对"金额相同 + 供应商相同 + 日期相近"设硬规则。

**3. 风险评估**
- 阈值降低会显著增加 FP，需配合人工复核队列。
- 模糊匹配可能把正常分期付款误判。
- 需在 fixture 上做 precision/recall 曲线调优。

---

### 失败 #5 — expense / exact-duplicate-invoice / FP

**1. 根因推测**
`exact-duplicate-invoice` 去重键可能只用 `invoice_number`，未包含 `vendor_id` 或 `invoice_date`。complex_03 中不同供应商可能使用相同发票号（尤其手写/纸质发票）。

**2. 修复方向**
- 去重键改为复合键：`(vendor_id, invoice_number, invoice_date, amount)`。
- 增加**发票号格式校验**：不同供应商的编号规则不同，跨供应商同号不报。
- 对同一供应商同号但金额不同，标记为"疑似篡改"而非"重复"。

**3. 风险评估**
- 复合键过严会漏掉"同号不同供应商"的真实欺诈（FN）。
- 需要 fixture 提供 vendor_id 字段。
- 建议保留"跨供应商同号"为低优先级告警。

---

### 失败 #6 — expense / policy-threshold / FP

**1. 根因推测**
`policy-threshold` 使用全局阈值（如单笔 >5000 需审批），但未按**费用类别**分桶。complex_03 中差旅/招待/办公的政策阈值不同，导致合规报销被误判。

**2. 修复方向**
- 引入**政策配置表**：`{category: {threshold, requires_receipt, requires_preapproval}}`。
- 按 `expense_category` 查表判断，而非硬编码。
- 支持**职级/地区**维度（如高管差旅标准更高）。

**3. 风险评估**
- 政策表需与业务同步维护，否则规则失效。
- 配置错误会导致系统性 FP/FN。
- 建议政策表版本化 + 单元测试覆盖。

---

### 失败 #7 — expense / submit-before-expense / FP

**1. 根因推测**
`submit-before-expense` 比较 `submit_time` 与 `expense_time`，但未处理**时区**或**日期格式**（如 `2024-01-01` vs `2024/01/01`），导致解析错误后误判。

**2. 修复方向**
- 统一时区为 UTC 或业务本地时区，解析时显式指定。
- 使用 `dateutil.parser` 或 `pandas.to_datetime` 容错解析。
- 增加**合理性缓冲**：允许 submit_time 早于 expense_time 若干分钟（如跨午夜场景）。

**3. 风险评估**
- 缓冲窗口过大会漏掉真实"先提交后补票"欺诈。
- 时区统一可能影响其他时间相关规则。
- 需在 fixture 中明确时间字段格式。

---

### 失败 #8 — procurement / split-order / FP

**1. 根因推测**
`split-order` 检测同一采购需求被拆成多单，但未按 **supplier_id + item_category** 聚合。complex_01 中不同供应商的正常多单被误判。

**2. 修复方向**
- 聚合键改为 `(requester_id, supplier_id, item_category, time_window)`。
- 增加"合并金额是否超过审批阈值"作为必要条件。
- 排除不同采购目的（如不同项目 WBS）的订单。

**3. 风险评估**
- 供应商维度过严会漏掉"跨供应商拆分"欺诈。
- 需要 fixture 提供 requester_id / WBS 字段。
- 建议输出"疑似拆分"并附合并金额证据。

---

### 失败 #9 — procurement / price-outlier / FN

**1. 根因推测**
`price-outlier` 按**全局均价**比较，但 complex_01 中不同物料价格差异大（如纸箱 vs 设备），高价物料被全局均值掩盖，真实异常未被捕获。

**2. 修复方向**
- 按 `item_category` 或 `item_id` 分组计算价格基线。
- 使用**同类物料历史价格**做对比（时间序列）。
- 引入**供应商维度**：同一物料不同供应商价格对比。

**3. 风险评估**
- 分组过细导致样本不足，统计不稳定。
- 新品无历史价格，规则失效。
- 需冷启动策略（如用类别均值兜底）。

---

### 失败 #10 — procurement / process-order-before-approval / FP

**1. 根因推测**
`process-order-before-approval` 比较 `order_time` 与 `approval_time`，但 complex_02 是紧急采购场景，**允许先下单后补审批**（emergency override），规则未识别该业务例外。

**2. 修复方向**
- 引入**紧急采购标记**：`is_emergency=True` 时豁免或降级告警。
- 检查是否存在**事后审批**记录（approval_time 晚于 order_time 但在允许窗口内）。
- 增加"审批补录"事件类型识别。

**3. 风险评估**
- 紧急标记可能被滥用为规避手段。
- 需要审计紧急采购的后续合规性（如是否补全审批）。
- 建议对紧急采购单独统计并设置上限。

---

### 失败 #11 — procurement / process-receipt-before-approval / FN

**1. 根因推测**
`process-receipt-before-approval` 未覆盖 complex_02 中的**收货事件类型**（如 `goods_receipt` vs `service_receipt`），或事件流中收货记录缺失导致规则未触发。

**2. 修复方向**
- 扩展事件类型枚举：`order / approval / receipt / invoice / payment`。
- 对每种事件类型建立**状态机**，检测非法顺序。
- 增加"收货早于审批"的显式规则，覆盖所有 receipt 子类型。

**3. 风险评估**
- 事件类型扩展可能引入新的 FP（如部分收货场景）。
- 需要 fixture 提供完整事件流。
- 建议用状态机统一管理，避免规则碎片化。

---

## 三、修复优先级建议

| 优先级 | 失败编号 | 理由 |
|--------|----------|------|
| P0 | #5, #7, #10 | 逻辑错误（去重键/时区/业务例外），修复成本低、收益高 |
| P1 | #1, #6, #8 | 需引入业务维度（项目/政策/供应商），影响面大 |
| P1 | #4, #9, #11 | FN 修复，直接提升检出率 |
| P2 | #2, #3 | 统计/窗口调优，需回归测试 |

---

## 四、系统性改进建议

1. **统一事件模型**：expense 与 procurement 共享 `event_type` 枚举与状态机，避免规则碎片化。
2. **业务上下文注入**：所有规则应支持 `project_code / cost_center / supplier_id / is_emergency` 等字段。
3. **规则分级输出**：区分 `confirmed / suspicious / info`，降低 FP 对业务干扰。
4. **回归 fixture 扩展**：为每个 finding_type 增加正/负样本，建立 precision/recall 基线。
5. **配置外置**：阈值、政策表、时间窗口全部外置为 YAML，便于业务调整。

---

**结论**：11 个失败中，**7 个源于"缺少业务上下文过滤"**（FP），**4 个源于"规则覆盖不足"**（FN）。核心修复方向是**引入业务维度 + 分层统计 + 事件状态机**，而非简单调阈值。建议按 P0→P2 分批修复，每批配套回归测试。
