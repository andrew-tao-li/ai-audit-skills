# 审计 Skill 失败案例分析报告

> 分析对象：11 个失败案例（8 个 false_positive + 3 个 false_negative）
> 涉及 Skill：`expense-audit`、`procurement-fraud`
> 分析维度：根因推测 → 修复方向 → 风险评估

---

## 全局观察（先看模式，再看个案）

在逐条分析前，先提炼出跨案例的**结构性信号**，这决定了修复策略的优先级：

| 信号 | 出现次数 | 含义 |
|---|---|---|
| `false_positive` 集中在 `complex_02/03` | 6/8 | 复杂 fixture 中"正常业务模式"被误判为欺诈 |
| `false_negative` 集中在 `near-duplicate` / `price-outlier` / `receipt-before-approval` | 3/3 | 检测器**阈值过松或规则缺失**，而非逻辑错误 |
| `split-*` 类规则同时出现 FP（expense）与 FP（procurement） | 2 | 拆分检测的**聚合窗口/维度**定义有系统性问题 |
| `*-before-*` 时序规则同时出现 FP 与 FN | 3 | 时序比较的**基准字段**（提交时间 vs 审批时间 vs 收据时间）语义混乱 |

**结论**：这不是 11 个独立 bug，而是 **3 类系统性缺陷** 在不同 fixture 上的投影：
1. **拆分检测（split）** 的聚合维度与窗口定义错误
2. **时序检测（before/after）** 的字段语义与容差错误
3. **异常值检测（outlier/duplicate）** 的阈值与归一化错误

## 失败案例逐条分析

### 失败 #1 — expense / complex_01_full_audit / FP / `split-expense`

**1. 根因推测**
`split-expense` 规则很可能按"同一供应商 + 时间窗口"聚合，但未排除**同一报销单内合法的多行明细**（如一次差旅的多张机票/酒店）。complex_01 是"全量审计"场景，包含大量正常的多行报销，被误聚合为"拆分规避审批"。

**2. 修复方向**
- 在 `run_expense_audit.py` 的 `detect_split_expense()` 中，聚合键应改为 `(submitter, vendor, approval_id)` 而非仅 `(submitter, vendor)`。
- 增加前置过滤：同一 `report_id` 内的多行明细不参与跨单拆分判定。
- 引入"拆分意图"信号：仅当**每笔金额均低于阈值且合计超过阈值**时才告警。

**3. 风险评估**
- 收紧聚合键可能**漏掉真实的跨单拆分**（攻击者可能故意分单提交）。建议保留"跨单"路径但降低其权重，而非直接删除。
- 需要回归测试 `complex_02_procurement_abuse`，确认不会把真实拆分也过滤掉。

---

### 失败 #2 — expense / complex_02_procurement_abuse / FP / `robust-outlier`

**1. 根因推测**
`robust-outlier` 使用 MAD 或 IQR 做稳健离群检测，但**未按费用类别分组**。complex_02 是采购滥用场景，其中"设备采购"金额天然远高于"办公用品"，被跨类别比较后误判为离群。

**2. 修复方向**
- 在 `run_expense_audit.py` 的 `detect_robust_outlier()` 中，按 `(category, department)` 分组后再计算中位数与 MAD。
- 对样本量 < N（建议 N=8）的分组，退化为"仅标记不告警"。
- 输出中附带 `peer_group_size` 与 `z_score`，便于人工复核。

**3. 风险评估**
- 分组过细会导致**每组样本不足**，离群检测失效（FN 风险上升）。
- 需与失败 #9（procurement price-outlier FN）联动设计，避免"分组太粗→FP，分组太细→FN"的两难。

---

### 失败 #3 — expense / complex_02_procurement_abuse / FP / `sequential-invoice`

**1. 根因推测**
`sequential-invoice` 检测"连号发票"，但未排除**供应商批量开票**的合法场景（如月末统一开票）。complex_02 中采购滥用场景混入了正常批量开票，被误报。

**2. 修复方向**
- 在 `detect_sequential_invoice()` 中增加"批量开票豁免"：若同一供应商在同一日内开出 ≥K 张连号发票且总额正常，降级为 info。
- 引入"连号 + 金额递增/递减"组合信号，仅当连号且金额呈可疑模式时才告警。

**3. 风险评估**
- 豁免规则可能被攻击者利用（故意制造"批量开票"假象）。建议豁免仅降低 severity，不直接 suppress。
- 需要与 #4（near-duplicate FN）联合调参，避免"放宽连号→漏掉近似重复"。

---

### 失败 #4 — expense / complex_02_procurement_abuse / FN / `near-duplicate`

**1. 根因推测**
`near-duplicate` 检测漏报，最可能是**相似度阈值过高**（如要求 >0.95），或**归一化不足**（未处理金额格式、日期格式、供应商名大小写/缩写差异）。complex_02 中的近似重复发票因字段微小差异逃过检测。

**2. 修复方向**
- 在 `detect_near_duplicate()` 中：
  - 对金额做数值归一化（去千分位、统一小数位）
  - 对供应商名做标准化（去后缀、缩写展开、大小写统一）
  - 相似度阈值从 0.95 降至 0.85，并引入**字段加权**（金额权重 > 日期 > 供应商）
- 增加"金额完全相同 + 日期相近 + 供应商相似"的**规则兜底**，不依赖纯相似度。

**3. 风险评估**
- 阈值降低会**显著增加 FP**，尤其与 #3（sequential-invoice FP）叠加时。
- 建议引入**双阈值**：0.85 触发告警，0.95 触发高优先级，人工复核分流。

---

### 失败 #5 — expense / complex_03_hr_falsified / FP / `exact-duplicate-invoice`

**1. 根因推测**
`exact-duplicate-invoice` 在 HR 伪造场景中误报，最可能是**未排除"同一发票被多次引用但属于不同报销周期"**的合法情况，或**未排除冲销/红字发票**。complex_03 是 HR 伪造场景，可能包含正常的重复引用（如跨月分摊）。

**2. 修复方向**
- 在 `detect_exact_duplicate()` 中增加：
  - 排除 `report_id` 相同但 `line_id` 不同的情况
  - 排除已标记为"冲销/红字"的发票
  - 排除跨报销周期的合法分摊（需业务字段支持）
- 输出中附带 `duplicate_context`（同单/跨单/跨周期），供人工判断。

**3. 风险评估**
- 排除规则过多会**漏掉真实的重复报销**（FN 风险）。建议保留"跨单 + 同金额 + 同日期"的高置信路径。
- 需要与 #4 联动，避免"exact-duplicate 放宽 → near-duplicate 也放宽 → 整体漏报"。

---

### 失败 #6 — expense / complex_03_hr_falsified / FP / `policy-threshold`

**1. 根因推测**
`policy-threshold` 检测"超政策阈值"，但未考虑**政策版本时效性**或**例外审批**。complex_03 中 HR 伪造场景可能包含"旧政策下的合规报销"或"已获例外审批的超标报销"，被误报。

**2. 修复方向**
- 在 `detect_policy_threshold()` 中：
  - 按 `expense_date` 匹配**当时生效的政策版本**，而非当前政策
  - 检查是否存在 `exception_approval_id`，若有则降级
- 政策表需增加 `effective_from` / `effective_to` 字段。

**3. 风险评估**
- 政策版本化改造涉及**数据模型变更**，可能影响其他规则。
- 例外审批字段若被滥用（伪造审批 ID），会引入新的攻击面。建议对 `exception_approval_id` 做真实性校验。

---

### 失败 #7 — expense / complex_03_hr_falsified / FP / `submit-before-expense`

**1. 根因推测**
`submit-before-expense` 检测"提交时间早于费用发生时间"，但未处理**时区差异**或**预提交/预审批**场景。complex_03 中可能包含跨时区提交或预审批流程，被误判。

**2. 修复方向**
- 在 `detect_submit_before_expense()` 中：
  - 统一时区（建议 UTC 存储，本地时区比较）
  - 增加容差窗口（如 ±24h），仅当超出容差才告警
  - 排除 `pre_approval=true` 的记录
- 输出中附带 `time_delta_hours`，便于人工判断。

**3. 风险评估**
- 容差窗口过大会**漏掉真实的时序欺诈**（FN 风险）。建议容差 ≤ 24h，并对超出 7 天的做高优先级告警。
- 需与 #11（procurement receipt-before-approval FN）联动，统一时序比较的基准字段。

---

### 失败 #8 — procurement / complex_01_ma_carton / FP / `split-order`

**1. 根因推测**
`split-order` 与 #1（split-expense）同源：按"供应商 + 时间窗口"聚合，但未排除**同一采购计划下的合法分批下单**（如 M&A 场景中的分批交割）。complex_01 是 M&A 纸箱场景，分批下单是正常业务。

**2. 修复方向**
- 在 `run_procurement_audit.py` 的 `detect_split_order()` 中：
  - 聚合键增加 `plan_id` / `contract_id`，同计划内的分批不告警
  - 引入"拆分意图"信号：仅当**每笔均低于审批阈值且合计超过阈值**时告警
- 与 expense 侧共享拆分检测逻辑，避免两套规则不一致。

**3. 风险评估**
- 与 #1 相同：收紧聚合键可能漏掉真实拆分。
- 建议将拆分检测**抽象为共享模块**，expense 与 procurement 共用，降低维护成本。

---

### 失败 #9 — procurement / complex_01_ma_carton / FN / `price-outlier`

**1. 根因推测**
`price-outlier` 漏报，最可能是**未按物料/品类分组**，或**样本量不足时未退化处理**。M&A 场景中纸箱价格可能因批量采购而异常低，但被全局中位数掩盖。

**2. 修复方向**
- 在 `detect_price_outlier()` 中：
  - 按 `(material_code, unit)` 分组计算基准价
  - 引入**时间衰减权重**，近期价格权重更高
  - 对样本量 < N 的分组，使用行业基准价或历史均价兜底
- 与 #2（robust-outlier FP）联动：expense 侧按 category 分组，procurement 侧按 material 分组，逻辑一致。

**3. 风险评估**
- 分组过细导致样本不足，需设计**分层兜底**策略。
- 时间衰减权重引入**参数敏感性**，需回归测试避免 FP 上升。

---

### 失败 #10 — procurement / complex_02_emergence / FP / `process-order-before-approval`

**1. 根因推测**
`process-order-before-approval` 检测"下单早于审批"，但未处理**紧急采购（emergence）**场景。complex_02 是紧急采购场景，先下单后补审批是合法流程，被误报。

**2. 修复方向**
- 在 `detect_process_order_before_approval()` 中：
  - 检查是否存在 `emergency_flag` 或 `post_approval=true`
  - 增加容差窗口（如审批在订单后 48h 内完成则豁免）
- 输出中附带 `approval_delay_hours`，便于人工判断。

**3. 风险评估**
- 紧急采购豁免可能被滥用。建议对 `emergency_flag` 做**频次限制**（如每月 ≤2 次）。
- 需与 #11（receipt-before-approval FN）联动，避免"放宽 order-before-approval → 漏掉 receipt-before-approval"。

---

### 失败 #11 — procurement / complex_02_emergence / FN / `process-receipt-before-approval`

**1. 根因推测**
`process-receipt-before-approval` 漏报，最可能是**规则缺失**（只检测 order-before-approval，未检测 receipt-before-approval），或**时序比较字段错误**（用了 order_date 而非 receipt_date）。complex_02 中收货早于审批的异常未被捕获。

**2. 修复方向**
- 在 `run_procurement_audit.py` 中**新增** `detect_receipt_before_approval()`：
  - 比较 `receipt_date` 与 `approval_date`
  - 与 #10 共享容差窗口与紧急采购豁免逻辑
- 统一时序检测框架：`(event_a, event_b, tolerance, exemption)` 四元组配置化。

**3. 风险评估**
- 新增规则会**增加告警量**，需与 #10 的豁免逻辑严格对齐，避免"order 豁免但 receipt 不豁免"的不一致。
- 建议将时序检测**抽象为共享模块**，expense 与 procurement 共用。

## 修复优先级建议

| 优先级 | 修复项 | 理由 |
|---|---|---|
| P0 | #4 near-duplicate FN、#9 price-outlier FN、#11 receipt-before-approval FN | FN 是审计系统的**核心风险**，漏报比误报更严重 |
| P1 | #1/#8 split 检测、#2/#9 outlier 分组、#7/#10/#11 时序框架 | 系统性缺陷，一次修复覆盖多个案例 |
| P2 | #3 sequential-invoice、#5 exact-duplicate、#6 policy-threshold | 个案修复，影响面较小 |

## 架构级建议

1. **抽象共享模块**：`split_detector`、`outlier_detector`、`temporal_detector` 三个模块，expense 与 procurement 共用。
2. **引入双阈值机制**：所有检测器输出 `severity`（info/warn/critical），人工复核分流。
3. **建立回归基线**：每个 fixture 的 FP/FN 数量纳入 CI，防止修复引入新问题。
4. **字段语义字典**：统一 `submit_date` / `approval_date` / `receipt_date` / `expense_date` 的语义与时区处理，避免时序类 bug 反复出现。
