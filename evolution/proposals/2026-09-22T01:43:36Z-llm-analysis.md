# 审计 Skill 失败案例深度分析报告

## 总览

11 个失败案例分布在两个核心 Skill 中：
- **expense-audit**：7 例（6 FP + 1 FN）
- **procurement-fraud**：4 例（2 FP + 2 FN）

**核心矛盾**：规则阈值类检测（threshold/outlier）过敏感导致大量 FP，而流程顺序类检测（before-approval）则出现 FN 说明状态机漏判。

## 失败 #1：split-expense（FP）

**Fixture**: `complex_01_full_audit` | **Skill**: expense | **类型**: false_positive

### 根因推测
拆单检测（split-expense）很可能基于"同一商户短时间内多笔接近阈值的小额交易"启发式，例如：
- 时间窗口过窄（如 ≤ 7 天）
- 金额聚类算法使用固定阈值（如单笔 < 500 但累计 > 500）
- 未考虑**合理拆单场景**（如多日出差分天报销、长行程分次加油）

### 修复方向
```python
# 当前疑似代码（run_expense_audit.py）
def detect_split_expense(transactions, threshold=500, window_days=7):
    # 仅按时间和商户聚合，未校验业务合理性
    ...

# 修复：增加业务白名单 + 上下文校验
def detect_split_expense(transactions, threshold=500, window_days=7):
    clusters = cluster_by_merchant_time(transactions, window_days)
    return [
        c for c in clusters
        if sum(c.amounts) > threshold
        and not is_business_whitelisted(c.merchant, c.category)
        and not has_substantive_receipt_variation(c)  # 多张不同发票 vs 同一张重复
    ]
```

### 风险评估
- **中**：增加白名单可能漏掉新型拆单；若 `has_substantive_receipt_variation` 实现不严，会被同一发票号多报规避。

## 失败 #2：robust-outlier（FP）

**Fixture**: `complex_02_procurement_abuse` | **Skill**: expense | **类型**: false_positive

### 根因推测
鲁棒离群点检测（如 MAD / IQR-based Z-score）将**真实的特殊采购**（例如紧急备用件、专用设备、非常规价格）误判为异常。可能原因：
- 样本量小但使用了严格的 Tukey fence（如 1.5×IQR → 3×IQR）
- 未引入"业务类别分层"——同一类别内的价格才可比
- 未对接"已审批的特殊采购清单"

### 修复方向
```python
# 修复：增加按 category × supplier 分层 + 审批白名单
def robust_outlier_score(amount, category, supplier):
    peers = get_peer_amounts(category, supplier)  # 同类同供应商历史
    if len(peers) < 5:
        return None  # 样本不足不判定
    median = np.median(peers)
    mad = np.median(np.abs(peers - median))
    if mad == 0:
        return None
    return abs(amount - median) / (1.4826 * mad)

# 调用前过滤 approved_special_procurements
```

### 风险评估
- **高**：放宽阈值或增加白名单会显著降低检测灵敏度。建议保留离群分数（连续值）输出，由人工复核阈值，而非硬编码。

## 失败 #3：sequential-invoice（FP）

**Fixture**: `complex_02_procurement_abuse` | **Skill**: expense | **类型**: false_positive

### 根因推测
连续发票号检测（sequential-invoice）将**正常的连续编号**误报。可能原因：
- 仅检测"发票号连续"，未校验金额/供应商/日期是否异常
- 未考虑**供应商发票号本身连续**（如月初批量开票、同一合同多期发票）
- 对小微供应商而言，连号是常态

### 修复方向
```python
# 修复：引入多维联合判定
def detect_sequential_invoice(group):
    if not is_number_sequential(group.invoice_nos):
        return None
    # 仅当以下条件同时满足时才告警
    return {
        'risk': 'sequential-invoice',
        'confidence': compute_confidence(
            same_supplier=group.same_supplier,
            amount_anomaly=is_amount_outlier(group),
            time_density=calc_density(group.dates),
            supplier_size=get_supplier_scale(group.supplier),  # 小供应商加分
        )
    }
```

### 风险评估
- **中**：将二元判定改为置信度分数需要下游消费方配合调整；需同步更新 investigation-assistant 的聚合逻辑。

## 失败 #4：near-duplicate（FN）

**Fixture**: `complex_02_procurement_abuse` | **Skill**: expense | **类型**: false_negative

### 根因推测
**严重问题**——明显应被发现的近似重复未被发现。可能原因：
1. **Hash 算法过严**：仅使用精确字段 hash（金额+日期+供应商），未使用模糊匹配（编辑距离、感知 hash）
2. **OCR/解析后字段不一致**：如同一发票被识别成 `¥1,200.00` vs `¥1200`，hash 不同
3. **图像层未比对**：附件图片未做 perceptual hash 比对

### 修复方向
```python
# 增加多层 near-duplicate 检测
def detect_near_duplicate(records):
    # Layer 1: 精确 hash
    exact = exact_hash_dedup(records)
    # Layer 2: 模糊匹配（金额 ±1%, 日期 ±3天, 供应商相似度 > 0.8）
    fuzzy = fuzzy_match(records, amount_tol=0.01, day_tol=3, supplier_sim=0.8)
    # Layer 3: 附件图像 perceptual hash（关键！）
    image_dups = phash_dedup(records.attachments)
    return merge_findings(exact, fuzzy, image_dups)
```

### 风险评估
- **中-高**：模糊匹配若阈值过松会复现 #1/#2 的 FP 问题。建议采用"召回优先 + 置信度分层"，低置信度走人工复核。

## 失败 #5：exact-duplicate-invoice（FP）

**Fixture**: `complex_03_hr_falsified` | **Skill**: expense | **类型**: false_positive

### 根因推测
精确重复发票检测过于严格，将以下情形误判：
- **同一笔出差的多人报销**（团建机票、集体培训费）
- **预付 + 实际报销**（先垫付后报销同一发票号）
- **同一合同的多份副本**（电子发票 PDF 重复提交）

### 修复方向
```python
# 增加上下文判定
def is_true_duplicate(record, existing):
    if record.invoice_no != existing.invoice_no:
        return False
    # 检查是否合法的同票多报
    if record.submitter == existing.submitter and record.expense_date < existing.expense_date:
        return False  # 合理：同人补报销
    if record.submitter != existing.submitter and is_group_event(record, existing):
        return False  # 合理：团建集体
    if record.submitter == existing.submitter:
        return True  # 同人重复提交 = 真异常
    return 'review'  # 跨人同票需人工
```

### 风险评估
- **高**：放宽条件可能让真正的 HR 伪造（HR 提交他人发票）漏过。必须区分"同人" vs "跨人"两种情形。

## 失败 #6：policy-threshold（FP）

**Fixture**: `complex_03_hr_falsified` | **Skill**: expense | **类型**: false_positive

### 根因推测
策略阈值（如单笔 > 5000 需 CTO 审批）检测报出大量 FP。原因：
- **未读取实际审批链状态**：只检测金额超限，未校验是否已有合规审批人
- **控件 vs 字段不一致**：检测的是字段值，但 UI 上由控件限制；解析时控件信息丢失
- **多币种/税前税后未归一化**

### 修复方向
```python
# 读取实际审批流并归一化
def check_policy_threshold(record, policy):
    normalized_amount = normalize_to_base_currency(record, policy.base_currency)
    if normalized_amount <= policy.threshold:
        return None
    # 必须存在有效审批人
    approvers = get_approval_chain(record)
    if not has_required_approver(approvers, policy.required_role):
        return {
            'risk': 'policy-threshold-breach',
            'severity': 'high',
            'evidence': {'amount': normalized_amount, 'threshold': policy.threshold}
        }
```

### 风险评估
- **低-中**：纯逻辑增强，副作用可控；但需保证审批链数据可信（避免被篡改的 approval 字段绕过检测）。

## 失败 #7：submit-before-expense（FP）

**Fixture**: `complex_03_hr_falsified` | **Skill**: expense | **类型**: false_positive

### 根因推测
"提交日期早于消费日期"误报。原因：
- **预付款**（订机票、订酒店）合法场景
- **系统时区差异**：跨时区出差
- **OCR 识别错误**：发票日期误读为更晚日期

### 修复方向
```python
def check_submit_before_expense(record):
    if record.submission_date < record.expense_date:
        # 排除预付款
        if record.category in PREPAYMENT_CATEGORIES:
            return None
        # 排除时区差异（>1天 才报）
        delta = (record.submission_date - record.expense_date).days
        if delta > -1:
            return None
        # 排除 OCR 置信度低的发票
        if record.date_ocr_confidence < 0.85:
            return 'review'
        return {
            'risk': 'submit-before-expense',
            'severity': 'high'
        }
```

### 风险评估
- **中**：预付款白名单若配置不全会漏报。建议改为"默认报，但区分 severity"。

## 失败 #8：split-order（FP）

**Fixture**: `complex_01_ma_carton` | **Skill**: procurement | **类型**: false_positive

### 根因推测
采购拆单检测（同一供应商短时间内多笔小订单绕过审批阈值）将真实业务误报。原因：
- **MA 纸箱采购**特性：JIT 配送、生产线分批叫料——本身就是小额高频
- 未识别 `ma_carton` 这类已知的**协议供应商**（contract supplier）
- 时间窗口/阈值硬编码不适合所有品类

### 修复方向
```python
def detect_split_order(orders, contracts):
    # 先按合约过滤
    contract_suppliers = {c.supplier_id for c in contracts if c.covers_categories('ma_carton')}
    candidates = [o for o in orders if o.supplier_id not in contract_suppliers]
    # 再做聚类
    clusters = cluster_by_supplier(candidates, window_days=14)
    return [c for c in clusters if sum(c.amounts) > threshold and len(c) > 1]
```

### 风险评估
- **中**：合约数据若未及时同步会产生新 FN。建议增加"未知供应商"作为兜底告警。

## 失败 #10：process-order-before-approval（FP）

**Fixture**: `complex_02_emergence` | **Skill**: procurement | **类型**: false_positive

### 根因推测
"先下单后审批"流程异常检测将**真实的紧急采购**误报。原因：
- 紧急采购（emergence）本身就走快速通道
- 未识别"紧急采购审批专用流程"（emergence PO 有独立审批模板）
- 时间差阈值过严（如 > 1 小时即报警，但紧急采购可能数天内补审批）

### 修复方向
```python
def check_order_before_approval(order):
    if order.created_at < order.approved_at:
        return None  # 正常
    # 区分紧急采购
    if order.is_emergence and order.emergence_approval_chain:
        grace_period = get_emergence_grace_period(order.priority)  # P1=24h, P2=72h
        if order.approved_at - order.created_at < grace_period:
            return None
    # 必须存在后补审批
    if not order.has_post_approval():
        return {'risk': 'process-order-before-approval', 'severity': 'high'}
    return {'risk': 'process-order-before-approval', 'severity': 'medium'}
```

### 风险评估
- **中**：紧急采购规则若被滥用，会成为新的舞弊入口。建议增加"紧急采购占比"监控指标。

## 失败 #11：process-receipt-before-approval（FN）

**Fixture**: `complex_02_emergence` | **Skill**: procurement | **类型**: false_negative

### 根因推测
**严重问题**——"先收货后审批"未被发现。与 #10 是镜像问题，但代码路径不同。可能原因：
- 收货（GR）模块与审批模块**数据源未打通**
- 收货状态更新走的是仓库系统（WMS），审计脚本未读取
- **紧急采购场景**下，审批常常延后，但收货先发生——这是一个真实存在但未被建模的状态

### 修复方向
```python
# 增加 WMS/GR 数据源接入
def cross_check_receipt_vs_approval(order_id):
    gr = wms_client.get_goods_receipt(order_id)
    approval = approval_client.get_approval_state(order_id)
    if gr.received_at and not approval.approved_at:
        delta = gr.received_at - order.created_at
        return {
            'risk': 'process-receipt-before-approval',
            'severity': 'high' if delta > SLA_THRESHOLD else 'medium',
            'evidence': {'received_at': gr.received_at}
        }
    if gr.received_at < approval.approved_at:
        return None  # 正常
```

### 风险评估
- **高**：依赖 WMS 数据可用性，若 WMS 不可达会导致审计盲区。建议增加 WMS 健康检查 + 离线缓存。

## 横向根因总结

| 类别 | 根因 | 涉及失败 |
|---|---|---|
| **规则阈值硬编码** | 未按品类/币种/业务上下文适配 | #1, #2, #6, #8, #10 |

## 修复优先级建议

1. **P0（数据完整性，立即修）**：#4、#9、#11 —— 三类 FN 均为高风险漏判
2. **P1（FP 控制，本迭代）**：#5、#7、#10 —— 影响审计可信度
3. **P2（规则优化）**：#1、#2、#3、#6、#8 —— 涉及业务知识梳理

## 通用架构建议

- 引入**置信度评分**替代二元判定，便于 investigation-assistant 做证据排序
- 抽取 `policy_engine` 子模块，统一管理阈值/白名单/分层逻辑
- 增加 **fixture-driven regression test**：将本表 11 个失败固化为 `tests/regression/` 用例，防止后续改动回退
