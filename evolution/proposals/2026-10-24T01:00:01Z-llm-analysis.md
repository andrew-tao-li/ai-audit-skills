## 失败 1 — `01_duplicate_invoice` / `exact-duplicate-invoice`

- **根因推测**
  - 去重逻辑可能仅按 `invoice_id` 查询数据库，而 fixture 中重复发票具有相同发票号但不同记录 ID，或反之仅按金额比较。
  - 也可能使用 `DISTINCT`、集合去重或严格相等，导致“发票号相同但日期/员工不同”的重复记录被吞掉。
  - 若逻辑要求完整字段一致，则会漏掉业务意义上的完全重复。
- **修复方向**
  - 在 `run_expense_audit.py` 的发票去重规则中增加多级键：
    1. 标准化发票号；
    2. 主键：`invoice_number + vendor + amount`；
    3. 辅助键：`invoice_number + employee + expense_date + amount`；
    4. 对规范化日期、金额和发票号进行归一化后再比较。
  - 将命中项作为 finding 输出，而非在预处理阶段直接去重。
- **风险评估**
  - **中风险**：可能把合法拆单、折扣发票或同号多币种记录误报为重复。
  - 需限制比较周期，例如仅检查同一会计期间或滚动 90 天。

## 失败 2 — `02_employee_date_amount` / `exact-duplicate-employee-date-amount`

- **根因推测**
  - 当前重复检测可能只使用 `invoice_id` 或整行哈希，未使用业务复合键。
  - 或代码仅在数据库层去重，fixture 的多条记录在同一文件中或由 API 分页返回，未进入重复检测。
- **修复方向**
  - 在审计记录加载后建立统一记录列表，并按以下键分组：
    ```python
    duplicate_key = (
        normalize_invoice_number(record.invoice_number),
        normalize_employee_id(record.employee_id),
        record.expense_date,
        round_money(record.amount),
    )
    ```
  - 分组内记录数大于 1 时生成 finding，并保留所有原始记录 ID。
  - 避免先执行 `drop_duplicates()`。
- **风险评估**
  - **低至中风险**：同一发票因多币种、退款、补录而出现相同复合键时可能误报。
  - 应排除负数退款与正数消费混合等特殊场景。

## 失败 3 — `03_sequential_invoices` / `sequential-invoice`

- **根因推测**
  - 未实现连续发票号检测，或者只支持固定前缀，如 `INV-`。
  - 规则可能仅比较发票号字符串完全相等，没有提取尾部数字。
  - 排序时可能按数据库默认顺序，而非自然数字顺序。
- **修复方向**
  - 增加 `sequential-invoice` 规则：
    - 从发票号提取数字部分；
    - 仅针对同一供应商、同一员工或同一时间段形成窗口；
    - 按数值排序后计算连续差值；
    - 对长度为 2 以上的连续序列生成 finding。
  - 将数字段解析封装为：
    ```python
    parse_invoice_number(value) -> (prefix, number, suffix)
    ```
  - 对带前导零的编号保留原始格式，避免把 `001` 与 `1` 简单视为同一编号。
- **风险评估**
  - **中风险**：供应商使用批次编号、分期付款或多部门拆票时容易误报。
  - 需要限定供应商、员工、金额相似度及时间窗口。

## 失败 4 — `04_format_anomaly` / `invoice-format-anomaly`

- **根因推测**
  - 发票号格式校验规则过严、过松或配置未生效。
  - 缺少对供应商自定义格式、纯数字格式、大小写及分隔符差异的归一化。
  - 规则可能只扫描固定字段，没有考虑 OCR/解析结果中的格式异常字段。
- **修复方向**
  - 在 `run_expense_audit.py` 中建立 `validate_invoice_format()`：
    - 统一去除空格和不可见字符；
    - 区分标准发票号、业务单号和供应商编码；
    - 检查长度、字符集、前后缀及异常重复符号；
    - 将格式异常作为低到中置信度 finding，而不是直接判欺诈。
  - 使用供应商级白名单配置，避免用单一正则覆盖所有供应商。
- **风险评估**
  - **中风险**：国际化发票、税务格式和供应商旧编号可能被误报。
  - 不应将格式异常单独作为高风险结论。

## 失败 5 — `05_holiday` / `holiday-signal`

- **根因推测**
  - 周末规则存在，但节假日日历未加载、时区不一致，或日期字段解析失败。
  - 节假日与周末共用规则时，节假日可能被周末逻辑覆盖但没有独立输出。
  - fixture 中日期可能是字符串，代码按 `datetime` 比较导致异常分支被跳过。
- **修复方向**
  - 将日期处理集中到 `parse_expense_date()`，统一返回本地时区日期。
  - 加载可配置节假日日历：
    ```python
    is_holiday(date, calendar, region)
    ```
  - 分别输出：
    - `weekend-signal`
    - `holiday-signal`
  - 对无法解析日期生成数据质量问题 finding，而不是跳过。
- **风险评估**
  - **低风险**：调休工作日、地区差异或跨境业务可能造成误报。
  - 日历必须带地区和年份版本，并支持工作日覆盖项。

## 失败 6 — `06_submit_before_expense` / `submit-before-expense`

- **根因推测**
  - 未比较 `expense_date` 与 `submitted_at/created_at`。
  - 比较逻辑存在字段名不一致、时区混用或仅比较日期而忽略时分秒。
  - 时间字段可能为空时，条件判断错误地把空值当作可比较值。
- **修复方向**
  - 增加时间线一致性检查：
    ```python
    if submitted_at < expense_at:
        emit("submit-before-expense", ...)
    ```
  - 全部时间先转为 UTC，再比较。
  - 对缺失或非法时间单独输出数据质量 finding。
  - 明确容忍时钟偏差，例如 5 分钟。
- **风险评估**
  - **低风险**：批量补录、离线提交、跨系统延迟可能产生表面倒序。
  - 建议只将明显早于消费时间的提交列为风险。

## 失败 7 — `07_future_date` / `future-date`

- **根因推测**
  - 未使用运行基准时间，或基准时间取自数据库旧数据而非当前时间。
  - 日期字符串解析导致比较失效。
  - 未来日期阈值过宽，导致测试日期仍被判定为合法。
- **修复方向**
  - 在 `run_expense_audit.py` 入口统一生成：
    ```python
    audit_now = datetime.now(timezone.utc)
    ```
  - 对 `expense_date > audit_now + tolerance` 输出 finding。
  - 如果测试需要固定结果，注入 `clock` 或 `AUDIT_NOW`，避免硬编码当前日期。
  - 同时处理未来时间戳和仅日期字段。
- **风险评估**
  - **低风险**：时区差、预录入和系统时钟偏差可能造成误报。
  - 可配置 1–24 小时容差，并保留审计时间来源。

## 失败 9 — `09_large_low_level` / `large-amount-low-level-approval`

- **根因推测**
  - 金额阈值未加载，或金额单位不一致（分/元）。
  - 审批级别字段使用字符串枚举，而代码期待数字或中文名称。

    required_level_for_amount(amount, policy)

  - 将审批级别映射为有序等级后比较。

- **风险评估**
  - **中风险**：币种、含税/未税、报销总额与单行金额口径不同会造成误报。
  - 政策必须按地区、币种和费用类型生效，并记录命中的具体条款。

## 失败 12 — `13_space_time_conflict` / `space-time-conflict`

- **根因推测**
  - 规则可能是位于 `procurement-fraud` 或 `investigation-assistant` 中，而 `expense` 审计入口未调用。
  - 未正确解析场地、起止时间或时区；仅按日期比较。
  - 冲突定义要求“同一员工 + 同一资源 + 重叠时间”，但代码遗漏员工或资源字段。
- **修复方向**
  - 在 `run_expense_audit.py` 中加入时空冲突规则：
    - 将时间区间统一为带时区区间；
    - 使用半开区间判断重叠：`start_a < end_b and start_b < end_a`；
    - 以 `(employee_id, resource_id)` 建索引；
    - 对异常结束早于开始、区间缺失单独报告。
  - 若该规则属于公共能力，应抽取共享模块供三个脚本复用，避免重复实现。
- **风险评估**
  - **中风险**：全天事件、不同城市同名场地、预订与实际消费记录可能产生误报。
  - 需明确“消费记录”和“预订记录”的数据来源及冲突容忍度。

## 失败 13 — `14_cross_period` / `cross-period`

- **根因推测**
  - 会计期间按自然月固定，但业务使用财年、结算周期或公司自定义期间。
  - 期间计算未使用发票日期、提交日期或入账日期，导致跨期记录没有进入相邻周期比较。
  - 仅按单条记录检查，未比较相邻期间的费用模式。
- **修复方向**
  - 引入可配置的 `AccountingPeriodResolver`：
    - 明确使用 `expense_date`、`submitted_at` 或 `posted_at`；
    - 支持自然月、财年和自定义结算周期。
  - 对比相邻期间内按供应商、员工、费用类型聚合的总额和笔数。
  - 将阈值配置化，避免硬编码金额。
- **风险评估**
  - **中高风险**：季节性业务、年度预提、项目周期和汇率变化均可能触发误报。
  - 该规则宜采用偏离基线的相对变化阈值，而非固定金额。

- **风险评估**
  - **中风险**：通勤、差旅高频消费和自动订阅会造成误报。

## 失败 16 — `auto_cross_employee_composite` / `cross-employee-invoice`

- **根因推测**
  - 复合 fixture 中同一发票跨多个员工、多个记录，规则要求字段完全相同，导致跨员工分组无法形成。
  - 记录可能因先被其他规则过滤、异常捕获吞掉或去重而没有进入检测。
  - 组合 finding 的生成依赖某单一子规则先成功，形成级联漏检。
- **修复方向**
  - 将基础规则独立执行，不要让 `policy-threshold`、`weekend-signal` 等规则成为跨员工规则的前置条件。
  - 按发票号聚合全部有效记录，再比较员工集合。
  - 在规则调度层增加“单规则失败不阻断其他规则”的异常隔离。
- **风险评估**
  - **中风险**：解除级联依赖后，更多单独信号会输出，可能增加告警量。
  - 可通过 finding 聚合机制把同一发票的多条信号合并展示，但不要删除基础信号。

- **风险评估**
  - **中风险**：不同城市价格和币种会导致阈值误判。

## 失败 18 — `auto_cross_employee_composite` / `weekend-signal`

- **根因推测**
  - 周末规则仅应用于交通或住宿的一部分记录，或在跨员工聚合后只检查首条记录日期。
  - 日期字段存在多格式，解析失败时跳过。
  - 规则执行顺序导致复合场景仅执行第一条 finding。
- **修复方向**
  - 对每条记录独立计算周末/工作日属性，再聚合信号。
  - 统一日期解析器并保留原始值与解析结果。
  - 确保规则引擎执行 `all rules -> collect all findings`，而非 `first match`。
- **风险评估**
  - **低风险**：跨时区航班或跨日住宿可能天然跨越周末。
  - 规则应描述“发生日期为周末”，不要将其自动等同于违规。
