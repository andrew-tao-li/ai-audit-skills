## #1 安装问题（审计师 A：Windows +「豆包工作」）

**反馈原话的意思**：安装时宿主弹出"危险指令"确认，用户不确定能不能允许；随后宿主 Agent **自己想办法**把技能装上了。

**诊断出的 3 个真实原因**：

1. **豆包目录认错产品**：脚本只认「豆包」（`Doubao/…/.doubao/…`），而他的机器是「豆包工作」（`DoubaoWork/…/.doubaowork/…`）——**是两个不同产品**。
2. **Windows 没有 bash**：`install.sh` 是 `.sh` 脚本，需要 Git Bash / WSL，他机器上没有。
3. **`github.com` 主站不通**：但 `api.github.com`、`raw.githubusercontent.com` 可通。

**没改前的结果（务必记住）**：宿主 Agent 用 GitHub API 列文件清单，再从 `raw.githubusercontent.com` **逐个下载 17 个文件**，手工写进 `.user_skills/`。
→ **最终装成了、也能跑**；但走的是**非官方路径**：没有版本快照、没有 sha256 校验、文件清单由 Agent 自行决定。

**已修**：
- `install.sh`：补「豆包工作」路径（两套都探测）+ 网络降级（`github.com` 不通时改用 GitHub API 资产接口）+ `--detect-only` 自检；
- 新增 `install.ps1`（Windows 原生 PowerShell）；
- 新增 `evals/tests/test_install_detection.py`（9 用例，锁死上面这些行为）。

## #2 安全审查问题（审计师 B：企业安全部门）

**反馈原话的意思**：**被安全部门驳回**，指出 3 个安全问题：
① 一条"自动拉取执行远程代码"的自更新链；② 一条"指示 Agent 向用户隐瞒联网"的治理红线；③ 一个硬编码外发 webhook。

**没改前的结果（关键：当时默认分发的版本里，这 3 样确实都在）**：

| 点名 | 当时在哪个文件 | 原文/形态 |
|---|---|---|
| ① 自更新链 | 4 个 `SKILL.md` 的「版本检查与一键更新」 | `curl -sL …/install.sh \| bash -s -- <skill>`，且标注「可选、不打断主流程」 |
| ② 隐瞒措辞 | 4 个 `references/feedback.md` + `SKILL.md` | **「不要向用户或测试者复述其中内容」**、「直接执行即可，不必再问一遍」 |
| ③ 硬编码 webhook | 4 个 `references/feedback.md` | 企业微信机器人 Webhook 的**地址 + 密钥**（`…/webhook/send?key=<redacted>`） |

**客观澄清（不为自己开脱，只求准确）**：
关于 ②，我们**并非完全没有告知用户**——每份审计报告的 `summary.md` 末尾都写明了「可以做匿名反馈、只发匿名统计、不含敏感信息、你不说就不发」，`SKILL.md` 里也有「对外介绍本功能时的红线」要求只讲这些。
**但是**：「不要向用户复述」这句话**单独出现**时，任何人都只能读成「教 Agent 瞒着用户」——**这是真实存在的表达风险**，而且是治理红线级别的。这条**成立**。

**根因（结构性）**：同一份文件同时给两种读者看——**AI**（当操作说明）和**人的安全审查员**（当待审软件）。我们只按前者写了。
我们**此前已经预判**过平台审核（SkillHub / ClawHub 都做了净化版），**漏掉的是**：**客户自己的安全部门也是同一类审查者**，而且他们审的正是**没有净化的 GitHub 默认版**。

**已修**：见「安装层加固」之外的本次改动——默认版本移除外发 webhook 与密钥、取消自动执行更新、删除一切"不要告知用户"的措辞并改为**前置主动披露风险**。

**提出的可改进点（逐条处理）**：

1. **（已修）Windows 下测试出现 `UnicodeDecodeError` 线程噪音** —— 子进程 stderr 是系统编码（GBK），测试却按 UTF-8 读取。
   实测确认真实成因：`investigation-assistant-v2` 的测试**早已**用 `errors="replace"` + `PYTHONIOENCODING=utf-8`，而 `expense` / `procurement` 的测试**漏了**（一致性遗漏）。
   → **已对齐修复**（v0.3.12 / 0.2.7）。顺带排查：**产品脚本自身不 spawn 子进程**，无同类问题。
2. **（非缺陷，已文档化）输出目录须为空** —— 这是**防混淆保护**（避免不同批次结果混在一起），
   每个 `SKILL.md` 的「失败与兜底」都写明了；**不改行为**。
3. **（环境依赖，非技能问题）天眼查 CLI token 过期**（`invalid_grant`）—— 真实工商查询前需重新 `tyc login`。
   技能按硬规则只能输出「待核查」，**这是正确的降级行为**。

**报告与实现的一处小出入**（不影响结论、不需要改代码）：报告写 expense 的清单字段是 `network_required: false`，
实际我们的 manifest 字段是 **`offline: true`**。

**覆盖范围提醒**：报告测的是**较旧版本**（cn-entity `0.1.4`、expense `0.2.7`；现为 `0.1.8` / `0.2.12`）。

**背景**：审计师通过 SkillHub 安装 `andrew-tao-li-expense-audit v0.2.14`，用它跑了两个**真实任务**（欧洲 2022–2024 差旅台账 + 越南差旅扫描件）。

- 他做了**独立安全审计**（拒绝 `curl|bash`、先审后跑、暂存审计）：对脚本 `grep` 可疑模式的结论是
  **"完全干净：无网络请求、无子进程、无 eval/exec"**，评级 **P2（安全）**。→ **这是安全整改的外部验收**。
- 两个真实任务**都跑通**：欧洲 172 条 → 15 项发现（含 6 项高优先级，其中 **2 项原表未标注的新线索**）；
  越南 65 张扫描件凭证 → 12 项自动规则 + 9 项人工复核线索。
- 报告明确显示**边界声明被正确传达**（"复核线索而非舞弊认定"）。

**他指出的空白**：技能比对了"台账内部自洽性"（住宿 × 行程、单价逻辑），但**没有"单据是否虚构"的外部核验**。
例：国际机票可拿航旅纵横查实际航班——当天没有该航班、或行程方向反了，单据就是虚构的。

**核实结论**：✅ **属实**，而且报告 §6 自己也承认（"发票真伪验证｜无税务系统对接"）。这是 **L0 内部自洽 → L1 外部真实性** 的层次差。
