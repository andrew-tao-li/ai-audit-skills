## 一、吸收了什么（已落地，全部为**可选开关**）

| # | 吸收的能力 | 它那边的做法 | 我们的落地 | 版本 |

## 二、明确**没**吸收的（及理由）

| 项 | 为什么不做 |
|---|---|
| 完整套件规模（24 技能 / 80k 行 / 4 平台插件） | 违背我们定下的「**不加新技能、维持最小可用**」 |
| 完整本体论（5 对象 YAML + 12 关系 + 11 Action + Hook 硬闸门） | 对"审计初筛 → 材料整理"过重；我们的扁平 CSV/JSONL 已够用 |
| MCP / OCR 云端连接器 | **破坏我们"脚本零联网"的卖点**，也违背企业安全整改基线 |
| Node.js hooks 依赖 | 我们坚持**纯 Python 标准库**，不引入新运行时 |
| 7 个分工代理 | 宿主不一定支持子代理；会显著增加编排复杂度 |
| 8 个 `fraud-*` 领域技能 | 与我们既有费用/采购技能重叠，且它们自己也多为 🚧 Alpha |

## 五、它身上值得继续学的两点（非技术）

1. **诚实标注成熟度**：它对 24 个技能逐个标 ✅Stable / 🧪Beta / 🚧Alpha，并说明配套完整度。我们目前没有这种标注。
2. **缺陷公开留痕**：它有 `docs/development-reports/`、`REVIEW-BUGS.md`、`REFACTOR-PLAN.md`，
   把自己的 bug 与重构计划公开写下来——与我们 `docs/reported-issues.md` 的做法一致，值得继续保持。
