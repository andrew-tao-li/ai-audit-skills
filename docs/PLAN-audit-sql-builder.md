## 一、场景来源（真实用户原话）

一位审计/监察的 **AI 推广者**在看了《AI 驱动的审计与监察实务》大纲后反馈：

> 「这个 AI 的应用最好能考虑到**数据库基础条件**」
> 「比如我们家的系统就挺 out 的，如果要依托我们的系统我估计**数据库功能很难满足 AI 要求**」
> 「所以我推 AI 就吃力，当然，可能还是我对 ai 不太了解」
> 「所以**扫盲**特别需要」

**读出来的真实痛点**：卡点不在 AI，而在**"从业务系统里把数据取出来"**这一环。
他们只知道**系统名字**，不知道怎么把数据变成可分析的表格。

---

## 二、收窄后的范围（用户明确要求"先在这个比较窄的场景上开发"）

> **"只知道系统名 → 拿到能分析的数据"**，中间那一步是 **SQL**。

用户给的"几步走"：

1. **和 IT 人员了解清楚系统的基本数据结构**（要一份数据字典）
2. **把审计需求翻译成 SQL 语句**，然后调取数据内容

**不做**：不做数据分析、不做审计判断（那是 `expense-audit-v2` 等已有技能的活）。
**做**：只负责把数据从业务系统"取出来"，然后**交给已有技能**去做审计。

---

## 三、CSV 能不能演示 SQL？（这是用户当时的疑虑，已想清）

**能。** 因为 SQL 不是数据，SQL 是**中间产物（一段文本）**。三类东西各归其位：

```
进：数据字典（CSV/XLSX）        ← IT 真的能导出：一张「表名 / 字段名 / 中文名」清单
 ↓
中间：生成的 .sql 文件（文本）    ← 技能的核心产出，贴给 DBA 跑
 ↓
出：查询结果（CSV）              ← DBA 跑完导出，直接喂给 expense-audit-v2
```

**所以 CSV 演示"进"和"出"，SQL 演示"中间那一跳"**——不冲突。

**额外优势**：测试里可以**真的执行**这些 SQL——Python 自带 `sqlite3`，不装任何数据库就能建合成库、
跑生成的 SQL、**比对结果行**。这样 SQL 不只是"看起来对"，而是"测过是对的"。

## 四、设计

### 名称
`audit-sql-builder`（中文可叫「审计取数」；名字可再定）

### 用户流程（技能要做的事）

```
① 用户说：系统叫「XX 财务系统」，我要查重复报销
② 技能说：先向 IT 要一份「数据字典」（表名+字段名+中文名），CSV 就行
③ 用户把数据字典丢进来
   → 技能【猜字段映射】：工号≈EMP_NO、金额≈AMOUNT、发票号≈INV_NO…（**给候选+置信度，不硬猜**）
   → 技能【列还缺什么】：字典里没有「发票号」→ 明确说"你得回 IT 确认"
④ 用户拿候选映射去跟 IT 对一遍（**这一步必须人工**，技能不替用户确认）
⑤ 技能【生成 SQL】：每条审计需求一个 .sql 文件，带注释
⑥ 用户把 SQL 给 DBA 跑 → 导出 CSV
⑦ 把 CSV 喂给 expense-audit-v2 → 出审计结论（**闭环**）
```

### 输入

| 参数 | 内容 |
|---|---|
| `--schema` | **数据字典**（CSV/XLSX）：`表名, 字段名, 类型, 中文名, 备注`（最少前两列） |
| `--map`（可选） | 字段映射 JSON；不给则先由技能**产出建议映射** |
| `--need`（可多选） | 要生成哪些审计需求的取数 SQL |
| `--dialect` | `mysql` / `oracle` / `sqlserver` / `postgres` / `sqlite`（**"系统挺 out"多半是 Oracle 或 SQL Server**） |
| `--output` | 输出目录 |

### 确定性核心（必须遵守：脚本只算事实，**不调任何 LLM**）

内置一份 **「审计需求 → SQL 模板」库**（`assets/sql_templates.json` + `references/sql-catalog.md`）：

| 需求 | 需要哪些字段 | 产出 |
|---|---|---|
| 重复报销 | 工号 + 发生日期 + 金额 | 捞出"同人同日同金额"的 SQL |
| 发票号重复 | 发票号 + 金额 | … |
| 超制度上限 | 金额 + 费用类型 | … |
| 周末消费 | 发生日期 | … |
| 拆单嫌疑 | 工号 + 发生日期 + 金额（窗口聚合） | … |
| 自审自批 | 工号 + 审批人 | … |

脚本做**纯字符串渲染**：把模板里的 `{{employee_id}}` 换成字典里找到的真实字段 → 生成 SQL。
**没有 LLM，结果确定可复现。**

**缺字段时绝不硬凑**——明确报"这个需求需要『发票号』，你的数据字典里没有"。

### 输出

```
out/
├── sql/01_duplicate_invoice.sql     ← 给 DBA 跑（带注释：依赖哪些字段、要注意什么）
├── sql/02_...sql
├── mapping.suggested.json           ← 拿去跟 IT 确认的字段映射（带候选与置信度）
├── missing_fields.csv               ← 还缺哪些字段（要回 IT 要）
├── summary.md                       ← 「几步走」落地指引
├── data_quality.md                  ← 数据字典本身的体检（哪些表缺主键、字段名可疑等）
├── run_manifest.json                ← 哈希 / 参数 / network_access: false
└── dashboard.html                   ← 全景图（沿用统一风格，第一屏执行摘要）
```

### 与已有 4 个技能的关系

**它是"第 0 步"**：不产出审计结论，只负责把数据取出来。取出后直接交给
`expense-audit-v2` / `procurement-fraud-v2` / `investigation-assistant-v2` / `cn-entity-relation-check`。
**这正好补上了用户截图里卡住的那一环。**
