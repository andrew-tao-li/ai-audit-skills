# 真实台账接入指南（字段映射与常见坑）

> 目标：把「公司真实的报销/差旅台账」接进来，而不必手工改数据。
> **本指南里的所有做法都是可选的**——不配置时，脚本行为与旧版完全一致。

---

## 一、字段映射（`--field-map`）

当表头不是脚本能自动识别的常见别名时，用一份 JSON 明确告诉脚本「哪列是什么」：

```bash
python3 scripts/run_expense_audit.py \
  --input 差旅报销单.xlsx \
  --field-map my_map.json \
  --output ./out
```

```json
{
  "expense_id": "单据编号",
  "employee_id": "工号",
  "expense_date": "费用发生日期",
  "submit_date": "提交日期",
  "amount": "小计",
  "expense_type": "费用类型",
  "vendor_name": "商户/供应商",
  "status": "审批状态"
}
```

- 核心字段：`expense_id` / `employee_id` / `amount` / `expense_date`（缺一个且无法自动识别时会报错并提示）。
- 其余字段（`status` / `vendor_name` / `expense_type` / `submit_date` / `invoice_number` …）按需映射，缺省即跳过对应规则。
- 完整字段与中英文别名见 [数据合同](data-contract.md)。

---

## 二、常见坑 ①：金额分散在多列

差旅报销单常长这样：

| 单据号 | 工号 | 机票 | 火车 | 住宿 | 市内交通 | 其他 | **小计** |
|---|---|---|---|---|---|---|---|
| T001 | E01 | 1200 | | 800 | 120 | | **2120** |

**做法 A（推荐）：映射到「小计」列**

```json
{ "amount": "小计" }
```

**做法 B：没有小计列时，让脚本求和**

在 `policy.json` 里列出要相加的列（仅当该行没有单一金额列时才生效）：

```json
{ "amount_columns": ["机票", "火车", "住宿", "市内交通", "其他"] }
```

> ⚠️ 两者取其一即可。**有「小计」就优先用它**（它代表申报口径，与你相加可能不等）。

---

## 三、常见坑 ②：表头不在第一行

有些导出文件第 1 行是筛选条件说明、第 2 行才是表头：

```
导出条件：2025年3月-2025年6月；部门=全部        ← 第 1 行（不是表头）
单据号,工号,费用类型,发生日期,金额,审批状态       ← 第 2 行（真正的表头）
T001,E01,差旅,2025-03-07,2120,已同意             ← 第 3 行起是数据
```

**当前版本要求表头在第一行**（`--sheet` 只能选工作表，不能选起始行）。处理方式二选一：

1. **预处理**：删掉第 1 行后另存为 CSV 再分析（最简单）；
2. **在 Agent 里做**：让宿主 Agent 读取后按标准列名另存一份——把这一步写进你的任务描述即可。

> 这条是已知边界，不是因为配置写错。

---

## 四、常见坑 ③：审批状态

真实台账的「已撤回 / 已拒绝」记录**默认也会参与分析**，这会让「同员工同日同金额」之类的规则产生大量假阳性
（一笔被撤回后重提的费用，看起来就像"重复报销"）。

配置后即可只分析你关心的状态：

```json
{ "status_filter": { "include": ["已同意"] } }
```

被排除的行不会消失——它们会完整列在 `excluded_by_status.csv` 里，并在 `data_quality.md` 中计数。
详见 [规则目录](rule-catalog.md) 的「审批状态过滤」一节。

---

## 五、常见坑 ④：发票号为空

没有发票号列时，`发票号重复` / `发票跨人复用` / `发票连号` 等规则会**自动跳过**，并在 `data_quality.md` 的
「警告与跳过规则」里明确列出——这不是漏检，而是输入里没有可比对的依据。

---

## 六、常见坑 ⑤：中文日期

v0.2.13 起支持这些写法（统一标准化为 `YYYY-MM-DD`）：

| 写法 | 示例 |
|---|---|
| **中文** | `2026年10月09日`、`2026年10月9日`、`2026年10月09日 12:30` |
| 分隔符 | `2026-10-09`、`2026/10/09`、`2026.10.09` |
| 紧凑 | `20261009` |
| 带时间 | `2026-10-09T12:30`、`2026-10-09 12:30` |

> 以前「年月日」识别不了，会被当成**坏行**进 `bad_rows.csv`——那一天相关的规则（周末、重复、拆单…）就全部失联了。

---

## 七、常见坑 ⑥：报销人身份（工号 还是 姓名）

`报销人` 可以是**工号**，也可以是**姓名**（`姓名` 列会被当作报销人身份；也可以在 `--field-map` 里把
`employee_id` 直接指到姓名列）。**但同一张表里只能用一种口径**：

- **报销人用工号、审批人用姓名** → 自审自批几乎必然漏检。v0.2.13 起会在 `data_quality.md` 的
  「警告与跳过规则」里**明确提示**「口径可能不一致」，**不会静默通过**。
- 想同时支持这两种：表里**同时提供**「工号」与「姓名」两列——自审自批按两者**任一命中**判定。

---

## 八、语义陷阱（真实审计师在实操里踩过的坑，**务必先确认**）

映射**语法上对**、**语义上错**，是产生大量假阳性的头号原因。跑规则前，**先打印表头 + 样本行**核对：

| 陷阱 | 后果 | 正确做法 |
|---|---|---|
| 把「**预订日期**」映射成 `submit_date` | 大量「提交早于消费」假阳性（订酒店本就早于入住） | 只把**报销提交日**映射为 `submit_date`；预订日期别映射 |
| 把「**凭证编号 / 订单号**」映射成 `invoice_number` | 大量「发票号重复」假阳性 | `invoice_number` 只放**真正的发票号**；没有就留空（相关规则会自动跳过） |
| 多晚订单直接拿**总额**比差标 | 3 晚 885 元被误判为"异常高额" | 提供 `nights` 列（技能会**自动派生间夜单价**），或跑"间夜单价口径"一轮 |
| 逐行/分档**差标**塞进 `policy.limits` | 报错或大量假阳性（`limits` 是**单一全局上限**） | 用台账里的**差标列** + `row_limit_check`（v0.2.22） |
| 行政区划粒度不符 | 沭阳县 ≠ 宿迁市 → 漏判/误判 | 先做市/县级归一，或统一到同一级 |
| 自定义注释键写进 `policy.json` | v0.2.21 之前会**直接报错退出** | v0.2.22 起 `_` 开头的键视为注释；**其它**未知键仍会报错（防静默忽略） |

> **一句话**：**先确认字段"是什么意思"，再决定它映射到哪**——这一步比调参重要得多。

## 九、自检清单

接入新台账后，先看 `data_quality.md`，确认：

- [ ] 「字段映射」是否符合你的预期（每列都对上了）；
- [ ] 「警告与跳过规则」里有没有你其实提供了、但没识别到的字段；
- [ ] 「警告与跳过规则」里有没有**口径提示**（如「审批人与报销人口径不一致」）；
- [ ] 「参与分析行数」与你的预期是否一致（排除状态/坏行后）；
- [ ] `excluded_by_status.csv`、`bad_rows.csv` 是否都是你能解释的行。
